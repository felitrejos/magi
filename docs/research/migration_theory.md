# Live state migration and workspace synchronization for handing off a running coding-agent session between hosts

Scope: theory and practice for moving a live coding-agent session (conversation, working tree, running processes) from one host to another on a LAN or Tailscale in seconds, including Mac to Linux. Research date: 2026-11-14.

## 1. Process and VM live migration: pre-copy, post-copy, hybrid; CRIU, DMTCP, Zap, Condor. Why application-level migration fits Mac to Linux

### Takeaway
Classic VM live migration (iterative pre-copy, then a short stop-and-copy) reaches tens to hundreds of milliseconds of downtime because only the "writable working set" has to move during the pause. That is the model to copy. Process-level checkpointing (CRIU, DMTCP, Zap) only works between compatible Linux hosts with matching binaries and resources, and cannot move a macOS process to Linux. For Mac to Linux, the only workable approach is application-level migration: serialize the agent's logical state (transcript, tool state), sync the files, and restart processes on the target.

### Cited Findings
**Clark et al. 2005, "Live Migration of Virtual Machines" (NSDI '05, Xen)**
- Iterative pre-copy: pages are copied over several rounds while the VM keeps running. Pages that are dirtied repeatedly (the "writable working set", WWS) are held back and sent in the final stop-and-copy. — [Clark et al., NSDI 2005](https://www.usenix.org/event/nsdi05/tech/full_papers/clark/clark_html)
- Stages: 0 Pre-migration, 1 Reservation (resources secured on B; if this fails the VM keeps running on A), 2 Iterative pre-copy, 3 Stop-and-copy (VM suspended on A, traffic redirected, remaining state sent), 4 Commitment (B confirms receipt and A may discard the VM; B becomes primary), 5 Activation. — [Clark et al. 2005](https://www.usenix.org/event/nsdi05/tech/full_papers/clark/clark_html)
- Measured downtime: Quake 3 server (64 MB VM) 60 ms, with 148 KB moved in the final phase. SPECweb99 (800 MB VM, 90% load) 210 ms of downtime and 71 s total migration; 18.2 MB remained at suspension, which took 201 ms to send plus 9 ms to resume. Static Apache (800 MB) 165 ms. The "diabolical" MMuncher workload had 3.5 s of downtime. — [Clark et al. 2005](https://www.usenix.org/event/nsdi05/tech/full_papers/clark/clark_html)
- Naive stop-and-copy of a 512 MB VM would need 32 s, 16 s and 8 s of downtime at 128, 256 and 512 Mbit/s. One pre-copy iteration cut downtime by at least 4x in the worst case and at least 16x for kernel compile and OLTP. — [Clark et al. 2005](https://www.usenix.org/event/nsdi05/tech/full_papers/clark/clark_html)
- Pre-copy stops when the computed rate exceeds the admin maximum or when less than 256 KB remains. Every workload has a small set of "hot" pages that are dirtied as fast as they can be sent, and these set a lower bound on downtime. Rate limiting adds 50 Mbit/s per round over the previous round's dirtying rate. Hosts were on switched Gigabit Ethernet. — [Clark et al. 2005](https://www.usenix.org/event/nsdi05/tech/full_papers/clark/clark_html)

**Post-copy and hybrid**
- Post-copy (Hines, Deshpande, Gopalan 2009) moves execution to the destination first and fetches pages on demand. It improved pages transferred, total migration time and network overhead compared with pre-copy on Xen. Using network faults as hints for pre-paging cut network-bound page faults to within 21% of the VM's working set for large workloads. Dynamic self-ballooning avoids sending free pages. The authors suggest post-copy suits large-memory or write-intensive workloads. — [Hines et al. 2009 (UMass-hosted PDF)](https://none.cs.umass.edu/~shenoy/courses/spring18/readings/hines09postcopy_osr.pdf)
- Hybrid adds a bounded pre-copy phase before switching to post-copy, which reduces later network-bound faults "as a large portion of the VM memory is already pre-copied." — [KVM/RDMA hybrid paper, Springer](https://springerlink.bibliotecabuap.elogim.com/content/pdf/10.1007/978-3-642-36949-0_63.pdf)

**CRIU**
- CRIU cannot dump: tasks that have opened or mapped character or block devices (except virtual ones such as null, zero and TUN); open files on lazy-unmounted filesystems; tasks with a debugger attached (gdb or strace); another user's tasks when run as non-root; sockets other than TCP, UDP, UNIX, packet and netlink; O_DIRECT pipes; corked UDP sockets; files passed over UNIX sockets; SysV IPC without an IPC namespace; and GUI apps connected to a real X server. File locks need `--file-locks`. External connections must be ignored on dump and recreated on restore. — [CRIU wiki: What cannot be checkpointed](https://criu.org/What_cannot_be_checkpointed)
- TCP connections are restored through kernel "TCP repair" mode. A Linux Plumbers talk calls this hard to extend and proposes an eBPF-based replacement (CRIB). — [LPC 2024 CRIB slides](https://lpc.events/event/18/contributions/1812/attachments/1622/3398/CRIB.pdf)
- GPU state is not handled natively. NVIDIA's `cuda-checkpoint` plus a CRIU plugin adds it, with limits: x64 only, single process, no UVM or IPC memory, and no GPU migration. — [NVIDIA blog: Checkpointing CUDA applications with CRIU](https://developer.nvidia.com/blog/checkpointing-cuda-applications-with-criu); [CRIU GPU Checkpointing](https://criu.org/GPU_Checkpointing)
- Agent-sandbox measurements: CRIU process checkpoints take about 700–1000 ms each, against about 20–100 ms for filesystem-only (ZFS) checkpoints. Under concurrency, 16 parallel 128 MB CRIU dumps took 1.3 s and 64 parallel 1 GB dumps took 47 s. — [Crab, arXiv 2604.28138 (HKUST, Apr 2026)](https://arxiv.org/html/2604.28138v1)

**DMTCP, Zap, Condor**
- DMTCP is user-level, unprivileged, and needs no kernel modules or patches. On 128 cores (32 nodes), checkpoint and restart typically took about 2 s, and forked checkpointing brought this to about 0.2 s. — [DMTCP paper, arXiv cs/0701037](https://arxiv.org/pdf/cs/0701037); [DMTCP SourceForge](https://sourceforge.net/projects/dmtcp/)
- Zap (Osman, Subhraveti, Su, Nieh, OSDI 2002) introduced the "pod", a group of processes with a private virtual namespace (virtual PIDs and network addresses), so pods can move between OS instances. It reported subsecond checkpoint and restart for an X desktop and an Apache server, implemented as a Linux loadable kernel module. This is the conceptual ancestor of containers plus CRIU. — [Zap, OSDI 2002](https://static.usenix.org/event/osdi02/tech/osman.html)

### Inferences
- Map these concepts onto an agent session. The "pages" are the files in the working tree plus the transcript. The WWS is the handful of files the agent edits each turn plus the newly appended transcript tail. The "hot pages" are files rewritten while a tool runs (build outputs, lockfiles, dev-server caches). The Clark result carries over directly: pre-copy everything while the agent runs, then pause at a turn boundary and ship only the residual delta. Downtime is then bounded by the delta size and RTT (on a LAN, often well under a second), not by repo size.
- Post-copy also has an analogue: start the agent on the target immediately and fetch files lazily, for example over a network filesystem or by pulling on first read. This is riskier for coding agents, because tools like `grep -r`, test runners and bundlers touch many files at once (a "fault storm"), and a source failure mid-migration loses state. Pre-copy plus a short stop-and-copy is the safer default. Hybrid only makes sense for very large, rarely touched trees.
- The Clark "Reservation" and "Commitment" stages are the cut-over protocol: verify the target can run the session (toolchain, disk, auth) before pausing, and keep the source authoritative until the target acknowledges.
- Mac to Linux: CRIU, DMTCP and Zap all assume a Linux kernel on both sides. A macOS process is a Mach-O binary using XNU syscalls, so its memory image means nothing on Linux. Cross-architecture (arm64 Mac to x86_64 Linux) memory images are impossible for any process-level tool. Even Linux to Linux, CRIU requires that open devices, external sockets (such as the LLM API's HTTPS connections) and GUIs be absent or recreated. For an agent, that rules out migrating the agent CLI process itself in the general case.
- Conclusion: migrate at the application level. The agent's real state is (a) the conversation and transcript (serializable JSON), (b) the working tree (files), (c) a small amount of harness state (permissions, todo list, cwd, env), and (d) running child processes (dev servers, watchers, test runs). For (d), record the command line, cwd and env, then restart on the target. Don't migrate the process image. Dev servers are designed to restart in seconds.

### Gaps
- No primary source found on HTCondor's checkpointing mechanism (standard universe) in this pass.
- The CRIU wiki page fetched does not state the cross-kernel-version or cross-CPU-feature restore requirements. The cross-architecture impossibility above is an inference, not a cited CRIU statement.
- Exact post-copy numbers (milliseconds of downtime, seconds of total time) from Hines et al. were not extracted from the full PDF.

## 2. Application-level checkpoint and restore for agents: papers, durable execution, LangGraph, context handoff, prompt caching

### Takeaway
2026 arXiv work on agent checkpointing (Crab, Planarian, AgentRewind, DeltaBox, Belayer) all checkpoint the environment (ZFS snapshots for files, CRIU for processes) alongside the LLM context. The central correctness hazard is restoring a filesystem that is out of step with the conversation. None of these papers specifically addresses cross-host live migration of an interactive coding agent. Durable-execution engines (Temporal, Restate, DBOS) and LangGraph checkpointers provide the right mental model: persist the conversation and tool results as an append-only journal and resume only at step boundaries. With server-side prompt caching, replaying the full transcript on the new host is cheap. It costs 0.1x the input price on a cache hit, and the cache is keyed on the request content rather than the host. So full-transcript replay generally beats summarization-based handoff for fidelity, and summaries should only be used when the context window forces it.

### Cited Findings
**Agent checkpointing papers (2026)**
- **Crab** (Wu, Chang, Cao, Gao, Wang, HKUST; arXiv 2604.28138, 30 Apr 2026) is a host-side checkpoint/restore runtime for agent sandboxes. It treats the agent as a black box, uses an eBPF inspector to infer which turns changed recovery-relevant state, and overlaps checkpointing with LLM wait time. It "raises recovery correctness from 8% (chat-only) to 100%" and "cuts checkpoint traffic by up to 87%". Checkpoint latency is p50/p95/p99 0.1/0.7/1.0 s. In a spot-migration test, checkpoint plus restore took under 1 s (median/p95 0.71/1.00 s). — [Crab, arXiv 2604.28138](https://arxiv.org/html/2604.28138v1)
- Crab's consistency hazard: a restore can pair a newer filesystem with older agent memory ("resumes at turn-2 progress while observing a turn-3 filesystem"). Crab fixes this with a coordinator that caches request/response pairs and returns synthetic responses to replayed requests until the agent catches up, without re-executing actions. — [Crab](https://arxiv.org/html/2604.28138v1)
- The "8% (chat-only)" figure means that restoring the conversation alone, without the matching environment, almost never yields a correct recovery. — [Crab](https://arxiv.org/html/2604.28138v1)
- **Planarian** (Guo, Chen, Vaswani, Paverd, Pietzuch; Imperial, IISc, Microsoft; arXiv 2609.35366, 28 Sep 2026) defines "statepoints": consistent, restorable point-in-time versions of local and remote environment state plus "state evidence". It uses Podman, CRIU for the process tree and ZFS for copy-on-write filesystem snapshots, and records compensating actions for remote (MCP and SQL) side effects. The LLM context is not rewound; a "restore context" is appended instead. Overhead is 1% on Terminal-Bench and 3% on DevOps and DB tasks. Incremental snapshots are up to 74x faster (memory) and 231x faster (filesystem) on an 8 GB working set. It does not discuss cross-machine migration. — [Planarian, arXiv 2609.35366](https://arxiv.org/html/2609.35366)
- **AgentRewind** (arXiv 2608.14380) records recoverable checkpoints of agent context plus controlled environment state, rolls both back, and injects memory of earlier attempts. — [AgentRewind](https://arxiv.org/html/2608.14380)
- **DeltaBox** (arXiv 2605.22781) does "millisecond-level" sandbox checkpoint and rollback by storing only deltas between consecutive checkpoints, for both filesystem and process memory. — [DeltaBox](https://arxiv.org/html/2605.22781v1)
- **Belayer** (arXiv 2608.14635) restores filesystem state, runtime state and LLM context from the same trajectory prefix for agentic RL fault tolerance. — [Belayer](https://arxiv.org/pdf/2608.14635)

**Durable execution as a model**
- Journal-based engines record each completed step in an append-only log. On recovery, the code re-runs from the top and recorded results are returned instead of re-executing. The surrounding code must be deterministic, and LLM outputs are stored and replayed, not regenerated. Replay does not prevent duplicate external side effects unless those effects are idempotent. — [tianpan.co: Durable agents](https://tianpan.co/blog/2026-04-23-durable-agents-async-queue-workflow-checkpoint); [agentwiki: durable execution for agents](https://agentwiki.org/durable_execution_for_agents) (secondary sources)
- DBOS checkpoints workflows into Postgres with no separate orchestrator. Restate persists every step before proceeding. Temporal records every activity call and its result in an event history. — [youngju.dev 2026 engine comparison](https://www.youngju.dev/blog/culture/2026-05-14-durable-execution-engines-2026-temporal-restate-inngest-trigger-dev-dbos-deep-dive-2026.en) (secondary)
- A counterpoint (ZenML's Kitaru) argues that journal replay's determinism constraints fit expensive, non-deterministic agents poorly, and uses cached checkpoints instead. — [ZenML: Why Kitaru doesn't use journal replay](https://www.zenml.io/blog/no-journal-replay)
- LangGraph saves a checkpoint per "super-step", keyed by `thread_id`. Successful node writes are persisted as task writes so they are not recomputed. Execution can only resume from a super-step boundary. A node containing `interrupt()` re-runs from its top on resume, so side effects before the interrupt can repeat (per a third-party write-up). — [LangGraph checkpointers docs](https://docs.langchain.com/oss/python/langgraph/checkpointers); [LangGraph persistence](https://docs.langchain.com/oss/python/langgraph/persistence.md); [levelup.gitconnected: node runs twice after interrupt](https://levelup.gitconnected.com/your-langgraph-node-runs-twice-after-interrupt-thats-by-design-99ad00fc48ef)

**Context transfer: full transcript versus summary**
- LLM summarization (compaction) is lossy, and the blocking summarization call stalls the agent. Aggressive summarization can lose the most recent insights, which then have to be rediscovered. — [Parallel Context Compaction, arXiv 2605.23296](https://arxiv.org/pdf/2605.23296)
- An empirical study comparing five compaction strategies in OpenCode across three frontier models found that default self-summarization was not beaten by any tested alternative. — [arXiv 2610.31778 (via Emergent Mind)](https://www.emergentmind.com/papers/2610.31778)
- A deterministic, LLM-free graduated eviction policy ran a single session through 89 sequential tasks across 80M tokens. — [Beyond Compaction, arXiv 2606.11213](https://arxiv.org/pdf/2606.11213)
- Codex uses a handoff-style compaction prompt that asks the model to write a summary for another LLM to resume the task. — [badlogic gist on coding-agent compaction](https://gist.github.com/badlogic/cd2ef65b0697c4dbe2d13fbecb0a0a5f)

**Prompt caching economics**
- Anthropic prompt caching: cache reads cost 0.1x base input. Writes cost 1.25x with the 5-minute TTL (default) and 2x with the 1-hour TTL. The cache covers the full prefix (tools, then system, then messages) up to the `cache_control` breakpoint, and the TTL is refreshed on each hit. — [Anthropic docs: Prompt caching](https://platform.claude.com/docs/en/build-with-claude/prompt-caching)

**Claude Code session state (practical)**
- Claude Code stores transcripts at `~/.claude/projects/<slug>/<uuid>.jsonl`, where the slug is the absolute cwd with `/` replaced by `-`. Resume only finds sessions when the project sits at the same absolute path, so moving to a different path or username requires renaming the slug folder and rewriting the recorded cwd. — [vincentschmalbach.com: migrate Claude Code sessions](https://www.vincentschmalbach.com/migrate-claude-code-sessions-to-a-new-computer/); [DEV: why you cannot copy a Claude Code session](https://dev.to/gowtham-sai-yadav/why-you-cannot-copy-a-claude-code-session-to-another-machine-2008)
- An issue reports that manually copying the files does not produce a working resume. `claude --teleport` pulls a web or cloud session into the local CLI, and one bug report says it drops up-arrow prompt history. There are open feature requests for native cross-device sync. — [anthropics/claude-code#18645](https://github.com/anthropics/claude-code/issues/18645); [claudeissues: teleport drops prompt history](https://claudeissues.com/issue/92734-teleport-web-local-handoff-drops-prompt-history-and-memory-resolves-to-a-differe); [claudeissues: cross-device session sync](https://claudeissues.com/issue/42219-feature-request-cross-device-session-sync-resume)

### Inferences
- The unit of migration should be the turn (or LangGraph super-step). Quiesce when no tool call is in flight and the last assistant message is complete. The journal is then complete and the working tree is stable, so this is the agent's natural "stop-and-copy" point. A pending tool call should either be allowed to finish, or be recorded as not-started so the target re-issues it. Never ship a half-executed shell command.
- The Crab and Planarian results show that the transcript and the working tree must be snapshotted atomically as a pair, with a version stamp tying them together (for example, the transcript turn index plus a tree hash). Restoring one without the other is the main correctness failure ("8% chat-only").
- Full-transcript replay is the high-fidelity default. Because the prefix cache is keyed on content, a target that sends byte-identical tools, system prompt and messages should hit the cache on its first call if it lands within the TTL. That makes handoff cost roughly 0.1x input on the cached prefix. Things that break byte-identity, and so silently cause a full-price cache miss, include absolute paths embedded in the system prompt (`/Users/x/...` versus `/home/x/...`), the OS name, the date, env-specific tool lists and MCP server sets. Normalizing or virtualizing these (for example, keeping the same repo path on both hosts) preserves the cache.
- Summarization-based handoff should be a fallback: when the transcript exceeds the target model's window, or when changing models (caches are per model). The literature finds summaries lossy, though self-summarization remains a strong baseline.
- Child processes (dev servers) should be described declaratively in the session state (command, cwd, env, port) and restarted on the target. Their in-memory state is disposable, unlike the agent's.

### Gaps
- No paper was found specifically on live migration of an interactive LLM coding agent between hosts. Crab's "spot-migration" test is the closest, and it is Linux-container to Linux-container.
- Whether Anthropic's prompt cache is shared across API keys, workspaces or regions was not verified. It is not stated here, but likely matters if the two hosts use different credentials.
- Primary Temporal, Restate and DBOS docs were not fetched. The descriptions above come from secondary blogs.
- Third-party claims of lower cache-read multipliers (0.05x or 0.025x) for newer models were not verified against Anthropic's pricing page.

## 3. Workspace sync: rsync, Mutagen, Syncthing, Unison, git-based, lsyncd, ZFS/btrfs send. Fastest correct cut-over; .env and node_modules

### Takeaway
For a correct, fast cut-over, use a continuously running watcher-driven sync (Mutagen, or rsync triggered by a watcher) for the working tree, plus a final synchronous "flush and verify" barrier at quiesce. Use git objects (a `git stash create` commit or a `git bundle`) to carry the exact HEAD, index and untracked tree content-addressably. Exclude `node_modules` and build outputs and rebuild them on the target, since they contain platform-specific native binaries. Ship gitignored-but-needed files (.env) through an explicit allowlist. Syncthing's default 10 s batching delay makes it a poor fit for a seconds-scale cut-over. Block-level ZFS or btrfs send is fast but requires the same filesystem on both ends, which rules it out for an APFS Mac.

### Cited Findings
- rsync (Tridgell and Mackerras, ANU TR-CS-96-05, June 1996) updates a file to match a remote copy by sending per-block checksums: a weak 32-bit rolling checksum (Adler-32 inspired, looked up through a 16-bit hash in a 2^16-entry table) and a strong 128-bit MD4. False alarms were under 1/1000 of true matches. — [ANU repository: The rsync algorithm](https://openresearch-repository.anu.edu.au/items/15a1c428-0ad3-49d6-bb54-9238250cbbf0/full); [tech_report.tex (Debian sources)](https://sources.debian.org/src/rsync/3.0.9-4/tech_report.tex)
- Mutagen combines the rsync algorithm with bidirectionality and low-latency filesystem watching, reconciling with a three-way merge. The default `two-way-safe` mode auto-resolves only conflicts that don't lose data. Unresolved conflicts stay in session state (`mutagen sync list`). Safety halts trigger on irregular conditions such as deletion of an entire sync root. — [Mutagen docs: File synchronization](https://mutagen.io/documentation/synchronization/); [Mutagen: Safety mechanisms](https://mutagen.io/documentation/synchronization/safety-mechanisms/)
- Mutagen's docs give no latency numbers. A third-party claim of a "40% reduction" with `two-way-resolved` is unsourced. — [datanovia Mutagen performance](https://www.datanovia.com/learn/tools/mutagen/performance-optimization.html)
- Syncthing's `fsWatcherDelayS` defaults to 10 s, meaning "it takes at least 10 seconds till the data is transferred to other devices". One user reduced discovery from 11 s to about 2 s by setting it to 1. Rescans in progress can add minutes. — [Syncthing config docs](https://docs.syncthing.net/users/config.html); [DEV: speed up Syncthing from 11 s to 2](https://dev.to/evoleinik/speed-up-syncthing-file-sync-discovery-from-11-seconds-to-2-345a); [Syncthing forum: watcher showdown](https://forum.syncthing.net/t/filesystem-watcher-showdown-base-vs-synctrayzor-vs-gtk/14665)
- ZFS and btrfs send/receive are block-level incremental sends between snapshots. Anecdotal numbers vary widely. In one 2014 report, `btrfs send -p` produced a diff in about 1 s but `btrfs receive` took 82 minutes. Btrfs requires read-only source snapshots. No controlled benchmark was found. — [lore.kernel.org btrfs receive slow](https://lore.kernel.org/all/20140915001836.GU8530@merlins.org/t/); [Vivian Voss: The snapshot that travels](https://vivianvoss.net/blog/the-snapshot-that-travels)
- Agent-sandbox research uses ZFS snapshots as the filesystem checkpoint primitive. Snapshot overhead stays within 22 ms each under high concurrency. — [Crab, arXiv 2604.28138](https://arxiv.org/html/2604.28138v1); [Planarian, arXiv 2609.35366](https://arxiv.org/html/2609.35366)
- Native binaries in node_modules: esbuild and similar packages install a platform-specific binary, and copying `node_modules` between platforms gives errors like "esbuild-linux-arm64 is present but this platform needs esbuild-darwin-arm64". pnpm's `supportedArchitectures` (`os`/`cpu` lists, including `current`) can install binaries for several platforms at once, and recent pnpm re-evaluates skipped optional deps when that setting changes. — [esbuild issue #1819](https://github.lhy31512.workers.dev/evanw/esbuild/issues/1819); [pnpm PR #7214](https://github.com/pnpm/pnpm/pull/7214); [pnpm CHANGELOG](https://cdn.jsdelivr.net/npm/pnpm@11.16.0/CHANGELOG.md)
- Git primitives (from the git reference): `git stash create` builds a stash commit (worktree plus index) without touching refs or the working tree, and `git stash store` or `git stash apply <sha>` can use it elsewhere. `git bundle create` packs refs and objects into a single file that can be fetched from like a remote. — [git-stash docs](https://git-scm.com/docs/git-stash); [git-bundle docs](https://git-scm.com/docs/git-bundle)

### Inferences
**Recommended design, a layered "pre-copy" for files:**
1. **Tracked and untracked source files.** Run a continuous Mutagen (or watcher plus rsync) session from source to target, excluding `node_modules`, `.next`, `dist`, `target`, `.turbo` and other caches. Use a one-way mode (`one-way-replica`) so the target is a pure mirror until cut-over, with no bidirectional conflicts. Flip direction only after the lease moves.
2. **Git state.** At cut-over, push HEAD and the branch via `git push` to the target (or a `git bundle` over the wire), and transmit `git stash create` output (or simply rely on the file sync plus `git update-index --refresh`). Git objects are content-addressed, so already-present objects cost nothing. That makes git the natural content-addressed layer for history. The file sync then carries only uncommitted and untracked deltas.
3. **Gitignored-but-needed files** (.env, .env.local, local certs). Use an explicit allowlist that is synced with secrets-aware handling (for example, Tailscale-only transport and file mode 600), or have each host fetch them from a secrets manager. Never blanket-sync gitignored files, because that would drag in `node_modules` and caches.
4. **node_modules and build outputs.** Rebuild on the target, don't sync. Native binaries make Mac-to-Linux copies wrong, not just slow. Keep the target warm: run `pnpm install --frozen-lockfile` on the target whenever the lockfile changes during pre-sync, so cut-over pays nothing. pnpm's content-addressed store makes this incremental. Linux-to-Linux on the same architecture could sync node_modules, but rebuilding from a warm store is still safer.
- **Final barrier.** At quiesce: pause the agent, ask the sync engine to flush (Mutagen has `mutagen sync flush`), then verify by comparing a tree hash such as `git ls-files -s` plus hashes of untracked allowlisted files on both sides. Only then transfer the lease. This is the analogue of Clark's "Commitment" acknowledgment.
- ZFS/btrfs send is excellent Linux-to-Linux, and a ZFS snapshot is the cheapest consistent point-in-time cut. It does not apply to an APFS source.
- Unison and lsyncd were not researched in depth in this pass. Unison is a two-way, rsync-like reconciler run in batch mode. lsyncd is inotify plus rsync, one-way, Linux-only for watching (an inference from general knowledge, not cited).

### Gaps
- No measured end-to-end numbers were found for Mutagen flush latency or rsync dry-run on a typical repo over Tailscale. A builder should benchmark (for example, `rsync -a --delete --dry-run --itemize-changes` time on a 50k-file tree with no changes, dominated by stat and file-list exchange).
- Unison and lsyncd specifics, and Docker/DevPod's use of Mutagen, were not verified with sources.

## 4. Continuous pre-sync (warm standby) and quiescing at a safe point

### Takeaway
Treat migration exactly like Clark pre-copy. Keep the target continuously mirrored (files, git objects, dependency installs, transcript append-stream) while the source agent runs. Then quiesce at a turn boundary with no tool call in flight, flush the tiny residual delta (the "writable working set" of the last turn), verify, and transfer ownership. Downtime then becomes milliseconds to low seconds, independent of repo size.

### Cited Findings
- Pre-copy's downtime is bounded by the residual dirty set at suspension. Clark's Quake server moved only 148 KB at stop-and-copy and saw 60 ms downtime. SPECweb moved 18.2 MB in 201 ms. — [Clark et al. 2005](https://www.usenix.org/event/nsdi05/tech/full_papers/clark/clark_html)
- Crab overlaps checkpointing with LLM wait time (the agent is idle while the model generates), and checkpoints only on turns that changed recovery-relevant state. — [Crab](https://arxiv.org/html/2604.28138v1)
- LangGraph can only resume at super-step boundaries. Partial node writes are stored so completed sibling work is not redone. — [LangGraph checkpointers](https://docs.langchain.com/oss/python/langgraph/checkpointers)
- Durable-execution journals persist each step before proceeding, making step boundaries safe resume points. — [youngju.dev engine comparison](https://www.youngju.dev/blog/culture/2026-05-14-durable-execution-engines-2026-temporal-restate-inngest-trigger-dev-dbos-deep-dive-2026.en)

### Inferences
- **Safe points**, from best to worst: (1) idle, waiting for user input; (2) between turns after the assistant message is fully written and no tool is pending; (3) while waiting on an LLM response, by cancelling the stream and re-issuing on the target, which is safe because no side effect has happened yet and the prefix cache makes it cheap; (4) during a tool call, which is not safe. Wait for completion, or for long-running tools (tests, builds) let the source finish and ship the result, or kill and re-run on the target if idempotent.
- **Stream the transcript.** Append each JSONL line to the target as it is written, so the transcript is pre-copied too. At cut-over only the last line or two remain.
- **Rate.** The agent's "dirty rate" is low: a few files per turn, with turns lasting seconds to minutes. This is far below LAN bandwidth, so pre-copy will always converge, unlike Clark's MMuncher. The exceptions are watchers and build tools writing to `dist/` or `.next/`. Exclude these so they don't create "hot pages".
- **Reservation check** before pausing: the target has the repo at the expected path, the toolchain resolves (`mise doctor` or a nix devshell evaluates), deps are installed against the current lockfile, the API credentials work, and free disk is sufficient. If any check fails, abort with the source still running.

### Gaps
- No published measurements of agent-specific "dirty rate" (files per turn) were found. A builder should instrument this.

## 5. Consistency and fencing: leases, fencing tokens, preventing split brain

### Takeaway
Use a lease for ownership of the session (and of the branch) plus a monotonically increasing fencing token (an epoch) that every side-effecting sink checks. Leases alone are unsafe because a paused or partitioned holder (a laptop lid closed mid-turn, then reopened) can still believe it is the owner. The token lets the resource reject stale writers.

### Cited Findings
- A lease is a claim about time, and process pauses (GC, suspend) can make a holder act after expiry. Heartbeats don't fix the pause problem. The fix is fencing tokens: the lock service issues an increasing number with each grant, and the protected resource rejects writes carrying an older token. The token source must be linearizable, so wall-clock timestamps and random UUIDs are unacceptable. — [Kleppmann's argument as summarized in BEE-19028 Fencing Tokens](https://alivedise.github.io/backend-engineering-essentials/distributed-systems/fencing-tokens); [DEV: distributed lock service, fencing tokens and failure modes](https://dev.to/gabrielanhaia/design-a-distributed-lock-service-fencing-tokens-and-the-failure-modes-29nl); [napolitain: distributed locking](https://napolitain.github.io/system-design/distributed-locking)
- Redlock-style locks are fine for efficiency (avoiding duplicate work) but not for correctness, because they don't support fencing. Antirez disputes this. — [Hazelcast: long live distributed locks](https://hazelcast.com/blog/long-live-distributed-locks/)
- Consensus-backed locks (Hazelcast FencedLock on Raft) preserve linearizability under partitions on the majority side. etcd ships an example demonstrating Kleppmann's scenarios. — [Hazelcast](https://hazelcast.com/blog/long-live-distributed-locks/); [etcd contrib/lock README](https://ftp.yandex.ru/mirrors/github/etcd-io/etcd/main/contrib/lock/README.md)
- Clark's protocol keeps host A authoritative until B acknowledges "Commitment"; only then may A discard state. — [Clark et al. 2005](https://www.usenix.org/event/nsdi05/tech/full_papers/clark/clark_html)

### Inferences
- **For a two-host personal setup**, a full Raft cluster is overkill. Options, in order of simplicity:
  1. A single coordinator (for example, a tiny service on the always-on homelab host, or a SQLite row) holding `{session_id, owner_host, epoch, lease_expiry}`. Handoff is a compare-and-swap that increments the epoch.
  2. Git itself as the fence: the agent's branch ref on a shared remote updated with `git push --force-with-lease=<branch>:<expected-sha>`, which is a compare-and-swap on the ref. A stale host's push fails.
  3. Embed the epoch in the transcript and the sync session: the target refuses to accept file sync or transcript appends tagged with an older epoch, and the source checks the epoch before every tool call and LLM call. If it has been fenced, it stops and goes read-only.
- **Fencing points**, the places that must check the token: before each tool execution (file write, shell), before each LLM call (so a resumed laptop doesn't spend tokens on a dead branch), on transcript append, and on git push. The file-sync engine should be one-way from the current owner. Reversing direction is part of the handoff transaction.
- **Ordering:** (1) target passes reservation checks; (2) source quiesces; (3) final flush and verify; (4) coordinator CAS to `owner=target, epoch+1`; (5) source sees the new epoch and becomes read-only (or exits); (6) target starts the agent loop with the new epoch. If the source is unreachable (a hard partition), the target may take over only after the lease expires plus a margin, and the epoch ensures the stale source can't write if it returns.

### Gaps
- Kleppmann's original 2016 post was not fetched directly. The findings come from faithful secondary summaries.

## 6. Terminal and session persistence analogues: tmux/screen, mosh SSP, Eternal Terminal

### Takeaway
These tools solve connection survival, not host migration. tmux and screen keep processes alive on one host when the client disconnects. Mosh (SSP) and Eternal Terminal keep the client-to-server channel alive across IP changes and sleep. None moves the server-side process to a different host. Their designs (state-object diffs in SSP, sequence-numbered replay buffers in ET) are good patterns for the handoff's control channel and transcript streaming.

### Cited Findings
- Mosh (Winstein and Balakrishnan, USENIX ATC 2012) is built on the State Synchronization Protocol (SSP), a UDP protocol that securely synchronizes client and server state even across client IP changes. SSP synchronizes objects that implement diff and patch rather than byte streams, uses AES-128-OCB, and adapts its frame rate to network conditions. — [Mosh paper (USENIX ATC '12)](https://www.usenix.org/conference/atc12/technical-sessions/presentation/winstein); [mosh paper PDF](https://mosh.org/mosh-paper.pdf); [ATC'12 slides](https://usenix.org/sites/default/files/conference/protected-files/winstein_atc12_slides.pdf)
- Mosh syncs only the visible screen (no scrollback), has no TCP fallback when UDP is blocked, and doesn't support `tmux -CC`. — [OpenReplay: 3 SSH alternatives](https://blog.openreplay.com/3-ssh-alternatives-unstable-connections/)
- Eternal Terminal implements resumable TCP. A BackedReader tracks bytes read (a sequence number), and a BackedWriter keeps an encrypted buffer of the last N bytes sent. On reconnect, each side reports its sequence number and the missing bytes are replayed. ET needs SSH for bootstrap (daemon on port 2022 by default) and keeps scrollback. — [Eternal Terminal: how it works](https://mistertea.github.io/EternalTerminal/howitworks); [OpenReplay comparison](https://blog.openreplay.com/3-ssh-alternatives-unstable-connections/)
- tmux keeps remote processes alive while ET or mosh keeps the connection alive, so the two are complementary. — [OpenReplay comparison](https://blog.openreplay.com/3-ssh-alternatives-unstable-connections/)

### Inferences
- A common "fake migration" is to always run the agent on the Linux host inside tmux (or Rex) and attach from the Mac. That avoids migration entirely, at the cost of the Mac being a thin client. A true handoff is only needed when the agent must run locally (offline use, local-only tools, or GPU and simulator access).
- ET's replay-buffer pattern maps directly onto transcript streaming: the target acks the last transcript line (sequence number) it has durably written, and the source resends from there after any reconnect. That gives exactly-once append without a separate protocol.
- SSP's "sync the latest state, skip intermediate states" idea suits UI mirroring (showing the live session on another device), but not the transcript, where every entry matters.

### Gaps
- Mosh evaluation numbers (keystroke latency improvements) were not extracted from the paper.

## 7. Cross-OS issues Mac to Linux: paths, case sensitivity, line endings, native binaries, toolchains

### Takeaway
The main cross-OS hazards are absolute-path dependence (Claude Code's per-project transcript key is the absolute cwd), native binaries in node_modules, and toolchain version drift. Use identical repo paths on both hosts (or a path-rewrite step), rebuild dependencies on the target, and pin toolchains with mise, asdf or a nix devshell so the target environment is reproducible.

### Cited Findings
- Claude Code keys sessions by absolute cwd (`~/.claude/projects/<cwd with / replaced by ->/<uuid>.jsonl`). A different path or username on the target means `--resume` will not find the session unless the folder is renamed and the cwd fields are rewritten. — [vincentschmalbach.com](https://www.vincentschmalbach.com/migrate-claude-code-sessions-to-a-new-computer/); [DEV: cannot copy a Claude Code session](https://dev.to/gowtham-sai-yadav/why-you-cannot-copy-a-claude-code-session-to-another-machine-2008)
- Platform-specific native packages (esbuild, and similarly swc, sharp, lightningcss, rollup native) break when node_modules is copied across OS or architecture. pnpm `supportedArchitectures` can co-install multiple platforms. — [esbuild issue](https://github.lhy31512.workers.dev/evanw/esbuild/issues/1819); [pnpm PR #7214](https://github.com/pnpm/pnpm/pull/7214)
- The OpenNext AWS build filters out non-Linux native binaries when packaging for Linux, showing that cross-platform node_modules needs explicit handling. — [opennextjs-aws PR #1117](https://gh.r-mj.com/opennextjs/opennextjs-aws/pull/1117)

### Inferences (general engineering knowledge, not sourced in this pass)
- **Paths:** `/Users/<u>/...` (macOS) versus `/home/<u>/...` (Linux). Fix with a symlink on Linux (for example `/Users/<u>` pointing to `/home/<u>`), or by placing repos under a common path such as `~/developer/<group>/<repo>` with the same username and a symlinked prefix. This also keeps system prompts byte-identical, which preserves the prompt cache. Transcripts also contain absolute paths in tool calls and results. These are historical and harmless if the same path resolves on the target.
- **Case sensitivity:** APFS is case-insensitive by default, Linux ext4 is case-sensitive. Files differing only in case can coexist on Linux but not on Mac, and imports with the wrong case work on Mac but fail on Linux. Sync tools should flag case-only collisions (Mutagen has case-conflict handling; not verified here).
- **Line endings:** not a Mac/Linux issue (both use LF), but `.gitattributes` with `text=auto eol=lf` guards against stray CRLF.
- **File modes, symlinks and xattrs:** the executable bit must be preserved (rsync `-a`; Mutagen's permission modes). macOS xattrs and resource forks (`._*` files, `.DS_Store`) should be excluded.
- **Toolchains:** pin Node, pnpm, Python and Rust via `mise.toml` or `.tool-versions` (asdf) or `flake.nix` devshells. Pre-install on the target during warm standby, and verify in the reservation step. Nix gives bit-for-bit reproducibility. mise/asdf give version pinning but rely on host libraries.
- **Ports and services:** dev servers bound to `localhost` on the Mac must rebind on Linux. If the user accesses them via Tailscale, bind to the tailnet IP or use `tailscale serve`.

### Gaps
- No primary sources were fetched for APFS case sensitivity, Mutagen's case-conflict behaviour, or mise and nix reproducibility claims. These are stated as inferences.
