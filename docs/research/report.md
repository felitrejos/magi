# Ship the transcript, not the process

A live Claude Code session can be moved from the MacBook to `homelab` in seconds today, but only by moving its *logical* state: the transcript JSONL and its sidecars, the git and working-tree state, and an explicit, encrypted set of secret files. You then start a fresh `claude --resume` on the far side, inside a Rex pane, with Remote Control switched on for the phone. No first-party feature does this. Remote Control keeps the session on the host where it started, `--teleport` only pulls cloud sessions down, and Desktop's "Open in" only pushes to Anthropic's cloud, carrying a summary rather than the transcript. The closest open-source attempts (twin, claude-sync, claude-code-sync) sync files without single-owner guarantees, and none of them carries secrets. Process migration is out of the question here: CRIU-class tools need a Linux kernel on both ends, and a macOS process image means nothing to Linux. The right model is therefore classic VM live migration done at the application level. Pre-copy everything while the agent runs, stop at a turn boundary, ship the small remainder, and hand over ownership under a lease with an epoch fencing token. For an open-source tool this gives three buildable tiers. The first is a `/handoff` skill plus a Stop hook that cuts over in roughly 5–15 s. The second is a pair of daemons that keep a warm standby and fence ownership, cutting over in roughly 2–4 s. The third is an agent-agnostic session-bundle spec with adapters and a self-hosted relay, so any client follows a session wherever it runs. Two decisions come first. You need to choose how files reach the homelab, because your own rule reserves plain SSH for when Rex is down. You also need a one-time homelab secrets and login bootstrap, which you can run now.

## Nothing on the market moves a live session between your own hosts

Anthropic ships four cross-host mechanisms, and none of them pushes a local CLI session to a machine you own. **Remote Control relays a session that keeps running where it started.** The local process makes outbound HTTPS calls to the Anthropic API, and phone, web and Desktop clients act as windows into it ([Remote Control docs](https://code.claude.com/docs/en/remote-control)). **CLI handoff is one-way.** `--teleport` pulls a cloud session into the terminal, but an existing terminal session can't be pushed anywhere. Teleport also needs a clean tree, a pushed branch and the same account, and messages that compaction summarised are not carried over ([cloud docs](https://code.claude.com/docs/en/claude-code-on-the-web)). The Desktop app's **Open in → Cloud carries the conversation only as a summary, and explicitly cannot move SSH or WSL sessions** ([Desktop docs](https://code.claude.com/docs/en/desktop)). Desktop *can* run Claude on `homelab` through an SSH environment, with a helper under `~/.claude/remote/` that survives the Mac sleeping. Those sessions start fresh, though, and run outside your Rex panes ([Desktop docs](https://code.claude.com/docs/en/desktop)). Self-hosted runners do move sessions between machines (the changelog mentions sessions "moved to a new machine" and a `runner_lost` spawn reason). They are a Team/Enterprise public beta, they only accept cloud-originated sessions, and they clone from a repo ([self-hosted environments](https://code.claude.com/docs/en/self-hosted-environments), [changelog](https://github.com/anthropics/claude-code/blob/main/CHANGELOG.md)). The demand is on record. Issue #51337 ("continue a session across machines") is closed, and #73639 ("transfer session to another claude code instance") is still open ([#51337](https://github.com/anthropics/claude-code/issues/51337), [#73639](https://github.com/anthropics/claude-code/issues/73639)).

The large open-source projects deliberately chose **"the agent stays put, clients come to it"** rather than migration. T3 Code (≈59.6k stars, MIT) states that a project and its threads belong to one environment, and that a repository identity can correlate clones across environments but never routes work between them ([T3 remote.md](https://github.com/pingdotgg/t3code/blob/main/docs/internals/remote.md)). Its cross-provider "handoffs" are text summaries capped at 240 characters per item, and it makes no claim of native context parity ([T3 context-handoffs.md](https://github.com/pingdotgg/t3code/blob/main/docs/internals/context-handoffs.md)). Happy (≈24.6k stars) wraps the CLI with a daemon and an end-to-end-encrypted relay whose server stores opaque blobs ([Happy encryption.md](https://github.com/slopus/happy/blob/main/docs/encryption.md)). `opencode serve` plus `opencode attach <url>` is a clean client/server split, but it too stays on one host ([opencode server docs](https://opencode.ai/v1/docs/server.md)). The tools that actually move bytes are small, young file syncers:

| Tool | What it moves | How it handles paths | Secrets | Single owner? |
|---|---|---|---|---|
| **twin** (created 2026-11-13, 0 stars) | Project, memory, transcript, checkpoints, todos, plans; Mac→Mac over rsync, best link first (Thunderbolt, LAN, Tailscale) | Same path on the other Mac; rewrites usernames inside transcripts | Never syncs credentials | A rule only: "do not open on both Macs" ([twin](https://github.com/crafter-station/twin)) |
| **claude-sync** (325 stars) | `~/.claude` sessions to R2/S3/GCS/WebDAV, age-encrypted | Translates project paths | n/a | Newer-wins, conflict commands ([claude-sync](https://github.com/tawanorg/claude-sync)) |
| **claude-code-sync** (103 stars) | `~/.claude` through a git repo | Per-machine project map, `__HOME__` tokens | Secrets denylist | Merge plus TUI conflict resolution ([claude-code-sync](https://github.com/perfectra1n/claude-code-sync)) |
| **claude-history-sync** (16 stars) | Conversations through Google Drive, plus Codex rollouts | Keyed by git remote URL plus relative subdir; skips repos with no remote | n/a | Newer mtime wins ([claude-history-sync](https://github.com/Edenzzzz/claude-history-sync)) |
| **claude-code-migrate** | Whole `~/.claude` plus a `~/.claude.json` snapshot | `sed` rewrites `/Users/<old>/` | n/a | One-shot; Linux untested ([claude-code-migrate](https://github.com/emreonal11/claude-code-migrate)) |
| **ccmanager** (1.3k stars) | Session data between worktrees on one host; `.worktreeinclude` carries `.env` | Same host | Within one host only | n/a ([ccmanager](https://github.com/kbwo/ccmanager)) |

None of them stops the agent cleanly, ships transcript, working-tree delta, untracked files and selected secrets as one atomic bundle, and guarantees that only one host owns the session afterwards. That combination is the gap your tool fills. The category's churn is a design constraint in its own right. Terragon shut down in January 2026, Vibe Kanban sunset its hosted services in April 2026 for lack of a business model, and Crystal was deprecated in February 2026 ([terragon-oss](https://github.com/terragon-labs/terragon-oss), [Vibe Kanban shutdown](https://www.vibekanban.com/blog/shutdown), [Crystal](https://github.com/stravu/crystal)). A tool that must outlive its authors' funding should need **no hosted service**: Tailscale plus the two machines is enough.

## Mac-to-Linux rules out process migration, so migrate at the turn boundary

Migrating the process itself is impossible here. CRIU cannot dump tasks holding real devices, non-standard sockets or a real X connection, and it restores TCP through Linux's TCP-repair mode ([CRIU: what cannot be checkpointed](https://criu.org/What_cannot_be_checkpointed)). DMTCP and Zap likewise assume a Linux kernel on both sides. A Claude Code process on the Mac is a Mach-O binary making XNU syscalls. Its memory image has no meaning on Linux, and if the homelab is x86_64 it has no meaning on that CPU either. The homelab's architecture was not checked, and the cross-architecture point is an inference rather than a statement from CRIU. Even Linux to Linux, the agent's long-lived HTTPS streams to the model API would have to be dropped and recreated. **The agent's real state is data**: the conversation journal, the working tree, a small amount of harness state (permission mode, tasks, plans) and descriptions of child processes. Data can be moved across operating systems.

The theory worth copying is Clark et al.'s Xen live migration. It pre-copies memory in rounds while the VM runs, holds back the "writable working set", and then stops and copies only the remainder. A Quake 3 server moved only **148 KB at stop-and-copy for 60 ms of downtime**. A loaded SPECweb VM moved 18.2 MB in 201 ms ([Clark et al., NSDI 2005](https://www.usenix.org/event/nsdi05/tech/full_papers/clark/clark_html)). Clark's stages map directly onto an agent handoff:

| Clark stage | Agent equivalent |
|---|---|
| Reservation | Check the target first: repo path, toolchain, deps installed for the current lockfile, `claude` logged in, disk free. The source keeps running if any check fails. |
| Iterative pre-copy | Stream transcript lines and file changes, push git objects, and run `pnpm install` when the lockfile changes |
| Stop-and-copy | Quiesce at a turn boundary and flush the last turn's dirty files and transcript tail |
| Commitment | Target verifies hashes and acks; ownership flips |
| Activation | Run `claude --resume` on the target |

An agent's dirty rate is a few files per turn, far below LAN bandwidth, so pre-copy always converges. The exceptions are watcher and bundler outputs (`dist/`, `.next/`), which must be excluded so they don't become "hot pages". Post-copy (start on the target and fault files in lazily) cuts total transfer for VMs ([Hines et al. 2009](https://none.cs.umass.edu/~shenoy/courses/spring18/readings/hines09postcopy_osr.pdf)). It is a poor fit for coding agents, though: `grep -r`, test runners and bundlers would set off a fault storm, and a source failure halfway through loses state.

The 2026 agent-checkpointing literature adds one correctness rule. Crab found that **restoring the conversation alone, without the matching environment, recovered correctly only 8% of the time, against 100% with both**. Its failure mode pairs a turn-3 filesystem with turn-2 memory ([Crab, arXiv 2604.28138](https://arxiv.org/html/2604.28138v1)). The transcript and the tree must therefore be stamped as one pair (last transcript record UUID plus a tree hash) and verified together. Planarian also shows a useful habit: it does not rewind the model's context. Instead it *appends* a "restore context" describing what changed ([Planarian, arXiv 2609.35366](https://arxiv.org/html/2609.35366)). "Safe to Resume?" warns that restored checkpoints can invalidate external effects ([arXiv 2608.29381](https://arxiv.org/pdf/2608.29381v1)). The safe points follow from all this. Best is idle at the prompt. Next is just after an assistant message has been fully written with no tool pending. Next is mid-LLM-stream, by cancelling and re-issuing, which is cheap because nothing has run yet. Never cut over in the middle of a tool call.

Ownership needs **a lease plus a monotonically increasing fencing token**. A lease on its own is a claim about time. A laptop whose lid closes mid-turn and reopens later still believes it holds the lease, and heartbeats don't fix that. The resource has to reject writers that present an older token ([fencing tokens summary](https://alivedise.github.io/backend-engineering-essentials/distributed-systems/fencing-tokens)). For two hosts a Raft cluster is overkill. A SQLite row on the always-on homelab, `{session, owner, epoch, lease_expiry}` updated by compare-and-swap, is enough. `git push --force-with-lease` acts as a second fence on the branch ref. Eternal Terminal's design also carries over. It keeps an encrypted replay buffer and resumes from the peer's last acknowledged byte sequence ([ET: how it works](https://mistertea.github.io/EternalTerminal/howitworks)). Use the same idea to stream transcript lines exactly once.

For the working tree, Syncthing's default 10-second watcher delay is too slow for a cut-over measured in seconds ([Syncthing config](https://docs.syncthing.net/users/config.html)). Mutagen pairs the rsync algorithm with low-latency watching and safety halts ([Mutagen docs](https://mutagen.io/documentation/synchronization/)). Run it as a one-way replica from the current owner and flush it at quiesce. `git stash create` produces a commit of worktree plus index without touching any refs, and `git bundle` packs refs and objects into a single file that can be fetched like a remote ([git-stash](https://git-scm.com/docs/git-stash), [git-bundle](https://git-scm.com/docs/git-bundle)). Never copy `node_modules` from Mac to Linux. Platform-specific native packages (esbuild, swc, sharp) break, so rebuild on the target from a warm pnpm store ([pnpm PR #7214](https://github.com/pnpm/pnpm/pull/7214)). ZFS or btrfs send would be ideal from Linux to Linux, but it cannot read an APFS source.

## A Claude session is one JSONL file plus sidecars, and every path inside is absolute

**Transcripts live at `~/.claude/projects/<encoded-cwd>/<session-uuid>.jsonl`.** The encoded cwd replaces every non-alphanumeric character with `-` and is truncated with a hash past 200 characters ([sessions docs](https://code.claude.com/docs/en/sessions)). Since v2.1.223, `claude --resume <id>` also searches every other project directory on the machine. That search only works when exactly one copy exists: a hand-copied duplicate makes resume report not-found. `claude --resume /abs/path.jsonl` resumes a file directly ([sessions docs](https://code.claude.com/docs/en/sessions)). Anthropic's own cross-host recipe for SDK apps is to persist the JSONL and restore it inside any directory under `~/.claude/projects/` on the new host before resuming. The same page states that session files are local to the machine that created them ([Agent SDK sessions](https://code.claude.com/docs/en/agent-sdk/sessions)). Anthropic also says the entry format is internal and changes between versions ([sessions docs](https://code.claude.com/docs/en/sessions)). The robust design therefore treats the JSONL as an opaque blob, copies it byte for byte, and pins the same or a newer Claude Code version on the target. The Mac CLI is 2.1.319 and Desktop-hosted sessions report 2.1.325. The homelab version was not checked.

A local, read-only inspection of this Mac fills in what the docs leave out. A 23 MB, 3,097-line transcript contained `user`, `assistant`, `attachment`, `system` (including `compact_boundary`), `file-history-snapshot`, `api-request` and `bridge-session` records. Nearly every message record carries an absolute `cwd`, plus `version`, `entrypoint` and `gitBranch`. An `environment` attachment snapshots platform, OS version, shell and working directory. The `bridge-session` record binds the transcript to a Remote Control session and to the owning account and organisation UUIDs. `file-history-snapshot` entries store an absolute `realParentDir` for `/rewind` backups held under `~/.claude/file-history/<uuid>/` (local observation, no URL). The documented state inventory gives the faithful transfer set, which includes the retention-swept sidecars `<uuid>/subagents/`, `<uuid>/tool-results/` and `<uuid>/mcp-tasks/` ([.claude directory docs](https://code.claude.com/docs/en/claude-directory)):

| Copy | Copy if wanted | Regenerate, never copy |
|---|---|---|
| `<uuid>.jsonl`, `<uuid>/subagents/`, `<uuid>/tool-results/`, `<uuid>/mcp-tasks/`, project `memory/` | `file-history/<uuid>/` (for `/rewind`), referenced `plans/` and `tasks/`, `uploads/<uuid>/`, the `~/.claude.json` project entry (trust, allowedTools, MCP enablement) re-keyed to the new path | `sessions/<pid>.json` and `*.key`, `session-env/`, `shell-snapshots/`, `daemon/`, `backups/`, `.credentials.json` and the Keychain item, `machineID` |

Resume restores the conversation (from the last compaction), model, agent, permission mode (except `bypassPermissions`), active goal and unexpired session-scoped scheduled tasks. **It does not restore background Bash or monitor tasks**, which come back only as "didn't finish" notes. It does not re-run interrupted tools or re-apply launch flags such as `--mcp-config`, `--settings`, `--plugin-dir` or `--add-dir` ([sessions docs](https://code.claude.com/docs/en/sessions)). Dev servers and watchers therefore have to be recorded as declarative launch specs (command, cwd, env keys, port) and restarted on the homelab. Running the same session ID in two processes interleaves their messages into one transcript ([sessions docs](https://code.claude.com/docs/en/sessions)), which is a split-brain you can see. That is exactly what fencing prevents.

### Path strategy decides both correctness and prompt-cache cost

The Mac encodes `/Users/felipetrejos/Developer/Personal/<…>`, while the homelab uses `~/developer/<group>/<repo>`. Every absolute path in the history is therefore stale on the homelab. The prompt cache makes the choice of fix expensive. The API caches by exact request prefix, scoped to the organisation (and, on some providers, the workspace) together with model and speed. It is not scoped to a host. Inside Claude Code, though, the cache is effectively per machine and directory, because the system prompt embeds auto-memory paths and the conversation opens with a cwd/platform/shell/OS announcement ([Claude Code prompt caching](https://code.claude.com/docs/en/prompt-caching)). On resume, Claude Code re-sends the whole conversation with the system prompt it started with, and it reads from cache whatever unchanged prefix is still within the TTL. On subscriptions the main conversation's TTL is 1 hour, otherwise 5 minutes ([Claude Code prompt caching](https://code.claude.com/docs/en/prompt-caching)). Cache reads cost 0.1× base input; writes cost 1.25× (5-minute TTL) or 2× (1-hour TTL) ([Anthropic prompt caching](https://platform.claude.com/docs/en/build-with-claude/prompt-caching)).

| Strategy | Mechanism | Prompt cache | `/rewind`, `~/.claude.json` | Risk |
|---|---|---|---|---|
| **Append, don't rewrite** (recommended for Phase 1) | Copy the JSONL byte for byte, run `claude --resume /abs/path.jsonl` from the homelab repo, and inject "you are now on homelab at …" as the first prompt or as SessionStart hook context | Prefix stays byte-identical, so the first call should hit if within TTL (inference, untested across hosts) | `/rewind` points at missing dirs; trust entry must exist for the new path | Model may occasionally reuse a stale `/Users/...` path |
| **Identical paths** (best long-term) | Lay the Mac out as `~/developer/<group>/<repo>` to mirror the homelab, then make `/Users/felipetrejos` resolve on Linux via a symlink or bind mount (needs `sudo`, so you run it) | Preserved; historical paths resolve | `realParentDir` resolves; project key can match | Node's `process.cwd()` likely reports the physical path, so a symlink may still change the encoded dir. A bind mount probably avoids this (unverified). Reverse direction needs a `/home` path on macOS (`synthetic.conf`, unverified) |
| **Rewrite paths** (what claude-code-migrate and twin do) | `sed` JSON-escaped paths in the JSONL, rename the project dir, re-key `~/.claude.json` | **The prefix changes from the first rewritten byte, so the whole context is re-cached at 1.25–2× once** | Fixed | Parses a format Anthropic calls internal; breaks across versions |

The cache arithmetic favours not rewriting. Rewriting a 150k-token context costs roughly one full-price cache write on the first homelab turn. Appending a note costs only the new tokens. `--exclude-dynamic-system-prompt-sections` moves per-machine sections (cwd, env info, memory paths, git status) out of the system prompt and into the first user message, which improves cross-host reuse for *new* sessions you intend to move (`claude --help`, v2.1.319, local observation). `CLAUDE_CODE_PROJECT_DIR_NAME` (v2.1.234+) pins a path-independent project directory name, but only together with `CLAUDE_CONFIG_DIR`, and that relocates settings and credentials too, so it means a fresh login on each host ([sessions docs](https://code.claude.com/docs/en/sessions), [authentication docs](https://code.claude.com/docs/en/authentication)). Three things remain unverified empirically: how Claude Code reacts when a resumed transcript's recorded `cwd` differs from the live one, whether a new `environment` attachment is inserted, and whether the cache actually hits across hosts. The first test of Phase 1 should resume a moved session and read `cache_read_input_tokens` from the first request.

## Rex launches and shows the session; Remote Control follows it to the phone; neither moves bytes

The two products are complementary, and the handoff should use both:

| | **Rex** (Superlogical, `0.1.0-preview.18`, closed source, beta) | **Claude Remote Control** |
|---|---|---|
| Role in handoff | **Launcher and observer**: finds the project session and repo tab on `homelab`, splits a labelled pane, runs `claude --resume`, waits, captures output, focuses the Mac app on it | **Phone and web attach**: registers the homelab `claude` process with Anthropic so claude.ai/code and the Claude apps can drive it |
| How it reaches homelab | `rex -S homelab …` over its built-in Tailscale integration; sessions keep running when clients disconnect ([Rex remote access](https://www.superlogical.com/rex/docs/linux/remote-access.md)) | Outbound HTTPS polling from the homelab process; no inbound ports ([RC docs](https://code.claude.com/docs/en/remote-control)) |
| Moves files? | **No.** No copy, scp or exec-with-stdin verb. `download_begin`/`upload_begin` are drag-and-drop byte streams needing an undocumented data-connection client. `rex forward` is documented but absent from preview.18 ([Rex CLI reference](https://www.superlogical.com/rex/docs/reference/cli.md); local `rex api describe`) | **No.** The transcript is stored on Anthropic servers while connected, but there is no export to another host |
| Can it start a resumed session elsewhere? | Yes: `rex -S homelab split … -- sh -c 'cd … && exec claude --resume …'` | No. `claude rc --session-id` takes the claude.ai URL ID, not the local transcript UUID ([RC docs](https://code.claude.com/docs/en/remote-control)) |
| Constraints | iOS client not in public testing yet; client actions such as `session.select` need the app's Remote Control setting, which is off by default ([Rex installation](https://www.superlogical.com/rex/docs/installation.md)) | Needs a full claude.ai login (no API key or `setup-token`); one RC session per interactive process; the process must stay running; directory must be trusted ([RC docs](https://code.claude.com/docs/en/remote-control)) |

The concrete launch sequence uses only documented Rex verbs from the local agent guide. Discover the repo tab with `rex -S homelab window ls -s <group> --json`, then find its shell block with `rex -S homelab block ls -s <group> --json`. Launch with `rex -S homelab split -s <group> -b <shell_block> --label 'claude: handoff <id>' --focus=false --json -- sh -c 'cd ~/developer/<group>/<repo> && exec claude --resume <path-or-id> --remote-control <repo>'`. Add `--interactive` if `claude` is only on PATH through `~/.zshrc`. A Rex pane on another host starts in `$HOME`, and `-c` with a missing directory does not report an error, so always `cd` inside the command (local `rex __internal skill`; [Rex agents doc](https://www.superlogical.com/rex/docs/automate/agent-skill.md)). Verify with `rex … capture --trim` and `rex … block call process`. Show the result on the Mac with `rex -S homelab -C <client> do session.select`. Rex's OSC 7501 Program Status Protocol can badge the tab as working, blocked or done ([Rex program status](https://www.superlogical.com/rex/docs/build/program-status.md)). Whether Claude Code emits OSC 7501 on its own is unverified, so a hook may need to emit it. Whether `--resume`, `--remote-control` and a positional prompt combine on one command line is untested.

Remote Control has three handoff-specific behaviours. First, the source must release it. Resuming in a second terminal while the first still holds RC prints "Remote Control not started here" ([RC docs](https://code.claude.com/docs/en/remote-control)), so the Mac process has to stop first. Second, **expect a new claude.ai entry after the move**. Whether a cross-host resume rebinds the transcript's recorded `bridgeSessionId` is undocumented. Messages queued through RC are held server-side and arrive "on the next resume" ([changelog](https://github.com/anthropics/claude-code/blob/main/CHANGELOG.md)), and that may mean the old binding. Third, the handoff pane is separate from the `claude rc --name <repo>` server already running in each repo tab. That server spawns *new* sessions and cannot adopt a local transcript, so the resumed session lives in a split pane next to it.

**Stopping the Mac side has no clean primitive.** No documented hook or command makes an interactive Claude Code process exit itself. A Stop hook can return `{"continue": false, "stopReason": "Handed off to homelab"}` to halt processing ([hooks docs](https://code.claude.com/docs/en/hooks)). The process still has to be ended by `/exit`, by `rex send-key … ctrl+c` aimed at its own Mac pane using `REX_SESSION`/`REX_BLOCK` from Rex's SessionStart hook (Rex's guide advises against sending input to your own pane, so this is a deliberate exception), or by running sessions under `claude --bg` and calling `claude stop <id>`. Desktop-hosted sessions have to be stopped from the app. Fencing hooks (Architecture 2) make this safe even when the process lingers.

### The file-transfer path conflicts with your homelab rule

Your CLAUDE.md says every homelab command goes through Rex and plain SSH is only for when Rex is down. `rsync … homelab:` and `tar | ssh homelab` both execute a server process on the homelab over plain (Tailscale) SSH. That is the fastest and simplest transport, and it is still a rule violation as written. **This is your call.** The options:

| Option | How | Speed | Fits rule? |
|---|---|---|---|
| A. Amend the rule: data-only transfers may use Tailscale SSH | Mac runs `rsync -az` / `tar \| ssh homelab` and Rex is used for every *command*. Tailscale SSH needs no `authorized_keys`, supports scp/sftp, can require IdP re-check, and revokes in seconds ([Tailscale SSH](https://tailscale.com/kb/1193/tailscale-ssh)) | Fastest; one round trip | Needs an explicit exception |
| B. Homelab pulls inside a Rex pane | `rsync mac:… ~/developer/…` or `git fetch` run in a labelled Rex split | Same speed | Yes, but the Mac must accept SSH (macOS Remote Login is a system setting you would turn on) or expose a git remote |
| C. Encrypted drop, Rex-pane receive | Mac age-encrypts the bundle to the homelab's key and drops it anywhere (Taildrop `tailscale file cp`, a private git remote, a shared dir); a Rex pane on homelab fetches and decrypts | Slightly slower; Taildrop details unverified this session | Yes. Because the payload is encrypted to the homelab key, the channel no longer matters for confidentiality |
| D. Rex `upload_begin` API | Implement Rex's data-stream client | Unknown | Yes, but the protocol is undocumented preview API. Not recommended |

The design below assumes **A for the hot path, with C as the rule-compliant fallback**. Encrypting every bundle to the homelab's age key is what makes C possible. The tool should expose a `transport = "ssh" | "rex-pull" | "drop"` setting so the rule stays yours to set.

## A2A delegates tasks; ACP and AG-UI attach clients; only a bundle format moves state

No protocol standardises "move a running agent's full internal state from host 1 to host 2", and the protocols divide cleanly by layer:

| Layer | Protocol | Fit for this tool |
|---|---|---|
| Task delegation between opaque agents | **A2A v1.0** (Linux Foundation; Task, `contextId`, Message/Part/Artifact; JSON-RPC, gRPC, REST) | **Wrong layer.** Opacity is a design principle: agents collaborate without access to each other's internal state, memory or tools. `contextId` is opaque. `historyLength` only caps how many messages come back, and messages are explicitly not a reliable delivery mechanism ([A2A spec](https://a2a-protocol.org/latest/specification/)). Carrying a transcript would need a custom Extension the spec gives no meaning to, and A2A cannot attach a UI to an existing session. IBM's Agent Communication Protocol merged into A2A in Aug 2025 ([LF press](https://www.linuxfoundation.org/press/a2a-protocol-surpasses-150-organizations-lands-in-major-cloud-platforms-and-sees-enterprise-production-use-in-first-year)) |
| Client ↔ coding agent attach | **ACP** (Zed's Agent Client Protocol, schema v1.31.0) | **Right layer for "any client follows the session."** `session/load` must replay the entire conversation, and `session/resume` reattaches without replay. Both take an absolute `cwd` and `mcpServers` ([ACP session setup](https://agentclientprotocol.com/protocol/session-setup)). The agent must already hold the session locally, so the bundle must land first. The stable transport is stdio only, and remote transport is still in progress ([ACP intro](https://agentclientprotocol.com/get-started/introduction)). `claude-agent-acp` exposes Claude Code with experimental list/resume/fork/delete ([claude-agent-acp](https://github.com/agentclientprotocol/claude-agent-acp)), and `acp-ui` wraps stdio agents as WebSocket endpoints ([acp-ui](https://github.com/formulahendry/acp-ui)) |
| App UI ↔ agent event stream | **AG-UI** (CopilotKit) | Snapshot-plus-tail semantics: `MessagesSnapshot` for resync after interruptions, `StateSnapshot` and JSON-Patch `StateDelta`, threads and runs ([AG-UI events](https://docs.ag-ui.com/concepts/events)). A good model for the relay's client feed |
| Tools | **MCP 2026-07-28** | Now stateless at the protocol level: no `initialize`, no `Mcp-Session-Id`, state lives in app-minted handles ([MCP blog](https://blog.modelcontextprotocol.io/posts/2026-07-28/)). MCP servers are simply re-launched from config on the target; only remote, shared servers keep handle state |
| Thread store | **Agent Protocol** / LangGraph, OpenAI Conversations | `threads/{id}/copy` and stream-join ([agent-protocol](https://github.com/langchain-ai/agent-protocol)); "history lives in a service any runner can pick up" ([OpenAI conversation state](https://developers.openai.com/docs/guides/conversation-state)). Patterns, not portable formats |
| Portable state file | **Letta `.af`** | The only real agent-state file format: history with `in_context` flags, memory blocks, tools, and secrets nulled on export ([agent-file](https://github.com/letta-ai/agent-file)). Letta-specific and unversioned, but the closest precedent for a bundle spec |

The conclusion is that state moves as a **file format plus a transport**, and clients reattach through **ACP or AG-UI semantics**. Claude Code's own Remote Control already implements the client-follow half for a single host: a relay, a server-stored transcript, and multi-device sync ([RC docs](https://code.claude.com/docs/en/remote-control)). An open equivalent that follows a session *across* hosts is the ambitious tier below. A2A belongs only at the very edge: an A2A agent could ask your tool to "continue context X on homelab". That is delegation, not migration.

## Secrets travel encrypted to the homelab's key and never into the agent's view

**Never copy Claude credentials.** On macOS the login sits in the Keychain. On Linux it lives in `~/.claude/.credentials.json` (mode 0600) ([authentication docs](https://code.claude.com/docs/en/authentication)). Copying an OAuth refresh token between machines is undocumented, and if refresh tokens rotate it could break the source's login (unverified). The obvious shortcut fails too: `claude setup-token` mints a one-year token that "can only make model requests", so it **cannot establish Remote Control sessions** ([authentication docs](https://code.claude.com/docs/en/authentication)). Since your homelab tabs run `claude rc`, the homelab needs its own `claude auth login` (press `c` to copy the URL, then paste the code back). The handoff tool should only *verify* that login exists and refuse to proceed without it. Logins warn three days before expiry, and RC sessions that outlive a login stop making progress ([authentication docs](https://code.claude.com/docs/en/authentication)). Note too that the transcript's `bridge-session` record names the owning account, so the homelab must be signed into the same account.

**Transcripts are the new leak vector.** If the agent ever ran `cat .env` or printed `env`, the plaintext values are sitting in the JSONL you are about to ship. Prevention comes in two layers. `Read` deny rules (`Read(./.env)`, `Read(./.env.*)`) cover the file tools and Bash commands Claude Code recognises (`cat`, `head`, `tail`, `sed`), but **not** `grep -r` or scripts that open files themselves ([permissions docs](https://code.claude.com/docs/en/permissions)). For OS-level enforcement, pair them with sandbox `filesystem.denyRead` and `credentials` deny or mask entries (bubblewrap on Linux, Seatbelt on macOS) ([sandboxing docs](https://code.claude.com/docs/en/sandboxing)). Detection is a gate: run `gitleaks stdin --redact` (or `trufflehog filesystem --no-verification`, so candidate secrets aren't sent to provider APIs) over the JSONL and sidecars before every transfer, and block on findings ([gitleaks](https://github.com/gitleaks/gitleaks), [TruffleHog](https://github.com/trufflesecurity/trufflehog)). gitleaks is now feature-complete and receives security patches only, with its author moving to Betterleaks. Redacting a finding in place changes the bytes and so costs one full cache re-write. Blocking and asking is the better default, and rotating the leaked key is the only real remedy anyway.

**Project secrets travel as an explicit, encrypted manifest.** SOPS supports dotenv files, multiple age recipients per path rule in `.sops.yaml` (laptop, homelab, offline backup), and even `ssh-ed25519` public keys as recipients. Key names stay plaintext and values are encrypted ([SOPS age docs](https://getsops.io/docs/usage/identities/age/)). For the per-handoff building block, the tool works out the needed secret-file set and compares SHA-256 hashes against the destination. It then streams only changed files as an age-encrypted tar to the homelab recipient, writes them with mode 0600, and prints only paths and counts. A repo that already uses SOPS, dotenvx (`.env.keys`), 1Password `op run` with a service account, or self-hosted Infisical/Phase needs nothing pushed. The tool only verifies that the target can decrypt or resolve ([dotenvx](https://dotenvx.com/docs/introduction/), [1Password CLI](https://www.1password.dev/cli/secrets-environment-variables/), [Infisical homelab](https://infisical.com/blog/self-hosting-infisical-homelab)). Self-hosting a secrets manager *on* the homelab turns it into the crown jewels. Keep dev or test credentials there, never production keys. Encryption controls who can read secrets from now on, but a reader that once held plaintext is only neutralised by rotating the upstream key.

### The one-time homelab bootstrap to run now

This bootstrap follows your Rex rule. Each homelab command runs as a labelled split in the `scratch` session (`rex -S homelab split -s scratch -b <SHELL_BLOCK> --focus=false --wait --keep-open --label 'claude: …' --json -- sh -c '…'`, then `capture`, then `block close`). Steps needing `sudo` are yours to type in a Rex pane. Package availability on Ubuntu was not verified this session.

```bash
# --- homelab (Rex scratch panes) ---
claude --version                      # pin >= Mac's 2.1.319 / 2.1.325
claude auth login                     # interactive: press c, paste code (you do this; never copy creds)
sudo apt install age                  # YOU run; sops + gitleaks: install from their GitHub releases if not in apt
mkdir -p ~/.config/sops/age && age-keygen -o ~/.config/sops/age/keys.txt && chmod 600 ~/.config/sops/age/keys.txt
age-keygen -y ~/.config/sops/age/keys.txt   # -> homelab public recipient "age1…"; paste into Mac config

# --- Mac (per repo; map Mac path -> homelab ~/developer/<group>/<repo> by normalized git remote) ---
cd ~/Developer/Personal/<repo>
git ls-files --others --ignored --exclude-standard -z \
 | grep -zE '(^|/)(\.env(\..+)?|\.dev\.vars|\.envrc|.*\.(pem|key|p8|p12)|credentials\.json|service-account.*\.json|google-services\.json|GoogleService-Info\.plist|\.npmrc|\.claude/settings\.local\.json)$' \
 | grep -zvE '(^|/)(node_modules|\.next|dist|target|\.venv)/|\.env\.(example|sample|template)$' > /tmp/secrets.list
gitleaks dir . --redact               # also flags non-obvious secret files the pattern missed
tar --null -T /tmp/secrets.list -czf - | age -r <homelab_age1…> -r <mac_age1…> > <repo>.secrets.tgz.age

# --- transport: Option A (Tailscale SSH, rule exception) or C (drop + Rex-pane pull) ---
# --- homelab (Rex pane in the repo's tab) ---
age -d -i ~/.config/sops/age/keys.txt <repo>.secrets.tgz.age | tar -xzf - -C ~/developer/<group>/<repo>
# chmod 600 the extracted files; diff key NAMES (not values) against .env.example
```

Finish by writing hardened homelab user settings: `Read` deny rules for `.env*` and `*.pem`, `sandbox.enabled`, and `sandbox.credentials.files` deny for `~/.claude/.credentials.json`, `~/.ssh` and `~/.config/sops/age/keys.txt` ([sandboxing docs](https://code.claude.com/docs/en/sandboxing)). Optionally convert each repo to SOPS with a `.sops.yaml` listing the Mac, homelab and an offline backup recipient, so that later handoffs only need to check that the target can decrypt.

## Three architectures, from a weekend skill to an agent-agnostic relay

All three share one invariant: **the unit of transfer is a turn-consistent pair (transcript tail record UUID plus working-tree hash), secrets travel only age-encrypted to the destination key, and exactly one host holds the session at any epoch.** The working name below is `baton`, with a `.baton` bundle. Check name collisions on GitHub, npm and crates before committing to it.

### Architecture 1: `/handoff` skill + Stop hook + rsync/git + Rex launch

The **components** are a user-only skill at `~/.claude/skills/handoff/SKILL.md` with `disable-model-invocation: true`, which gets `${CLAUDE_SESSION_ID}`, `${CLAUDE_PROJECT_DIR}` and `$ARGUMENTS` substituted and can run shell lines before the model sees anything ([skills docs](https://code.claude.com/docs/en/skills)). The skill writes a handoff flag. A `Stop` hook receives `session_id` and `transcript_path` on stdin and does the transfer *after* the turn has finished writing ([hooks docs](https://code.claude.com/docs/en/hooks)). A `baton-lite` shell script does the work, using rsync or git for transport and the Rex CLI for launch.

```text
/handoff homelab
 1 skill:   preflight via `!` lines — Rex reachable (rex -S homelab ls --json), homelab claude logged in & version >= local,
            repo mapped (normalized remote URL -> ~/developer/<group>/<repo>), age recipient known. Abort = nothing changed.
 2 skill:   write ~/.baton/pending/<session_id>; tell model "finish this turn, then stop".
 3 Stop hook (turn complete, JSONL final):
   a git:   git stash create -> SHA; push branch + stash ref to homelab remote (or bundle); record HEAD+tree hash
   b files: rsync -az --delete untracked allowlist (exclude node_modules,.next,dist,target,.turbo,.DS_Store)
   c gate:  gitleaks stdin --redact < <uuid>.jsonl (+ sidecars) -> block on findings
   d xfer:  <uuid>.jsonl, <uuid>/{subagents,tool-results,mcp-tasks}, memory/ -> homelab ~/.local/share/baton/<uuid>/
            (NOT under ~/.claude/projects to avoid duplicate-ID lookup); secrets diff as age stream
   e verify: remote sha256 of transcript + tree hash == local
   f launch: rex -S homelab split -s <group> -b <shell> --label 'claude: handoff <id>' --json -- sh -c \
            'cd ~/developer/<group>/<repo> && git stash apply <sha> && exec claude --resume ~/.local/share/baton/<uuid>/<uuid>.jsonl --remote-control <repo> "Resumed on homelab at ~/developer/<group>/<repo>; Mac paths in history map here."'
   g show:  rex -S homelab -C <mac_client> do session.select …
   h stop:  return {"continue":false,"stopReason":"Handed off to homelab"}; then rex send-key ctrl+c to own Mac pane (or /exit)
```

The **expected latency** is the end of the current turn plus roughly 5–15 s. That figure is an estimate and has not been benchmarked. Its parts are the rsync file-list scan (stat-dominated, so it scales with file count), the copy of a transcript that can reach 23 MB (it compresses well), the gitleaks pass, and Claude's start-up. Over a direct Tailscale path most of this lands in single-digit seconds. **What it can't do:** it has no protection against reopening the Mac copy, since there is no fencing and twin-style discipline is the only guard. It cannot cut over mid-turn. It cannot carry running dev servers, which must be relaunched by hand. `/rewind` breaks unless paths are identical, and Remote Control will likely show a new entry. It depends on an untested command line (`--resume` with an absolute path plus `--remote-control` plus a prompt), and on an unverified detail: where Claude appends new records when resuming from a path outside `~/.claude/projects`. Reverse handoff (homelab → Mac) is the same script with the hosts swapped.

### Architecture 2: `batond` daemons with warm standby, lease and epoch fencing

The **components** are a `batond` daemon on each host, reachable only over the tailnet, with the always-on homelab hosting the **coordinator**: a SQLite table `{session_id, project_id, owner_host, epoch, lease_expiry, consistency_stamp}` changed only by compare-and-swap. The daemons maintain a **warm standby** for every session marked "followable":

1. A transcript tailer streams appended JSONL lines to the standby copy with ET-style sequence acks, and incrementally gitleaks-scans each new line, so the full scan never sits on the critical path.
2. A Mutagen one-way replica of the working tree runs from the owner ([Mutagen](https://mutagen.io/documentation/synchronization/)), with git objects pushed continuously.
3. A lockfile watcher runs `pnpm install --frozen-lockfile` on the standby, so dependencies are already built when cut-over comes.
4. A toolchain check runs against `mise.toml` or `flake.nix`.
5. Secrets are kept in sync as age blobs, by hash diff.

**Path-independent project identity** comes from the normalised remote URL plus the repo's root commit SHA plus the relative subdir. Using the root commit covers local-only repos, which claude-history-sync simply skips ([claude-history-sync](https://github.com/Edenzzzz/claude-history-sync)). Identity maps to per-host paths in `~/.config/baton/projects.toml`.

**Fencing uses Claude Code's own hooks.** A `PreToolUse` hook and a `UserPromptSubmit` hook call the local daemon. If this host is no longer owner at the current epoch, they block the action with exit code 2 or a deny decision ([hooks docs](https://code.claude.com/docs/en/hooks)). A Mac reopened after a handoff therefore goes read-only instead of interleaving. On top of that, `git push --force-with-lease` fences the branch. Offline operation needs a policy. A laptop that holds the lease keeps working until the lease expires (say 24 h). If the homelab must take over while the Mac is unreachable, it waits for lease expiry plus a margin and then bumps the epoch. A returning stale Mac is offered `claude --resume --fork-session` plus a git branch, turning would-be split-brain into an explicit fork rather than a merge.

```text
baton move <session> homelab          (or /handoff, or a Rex action, or a phone shortcut hitting batond)
 1 reserve: target batond confirms standby lag==0 lines, deps current, claude auth ok, disk ok  -> else abort
 2 quiesce: source waits for idle/turn-boundary (sessions/<pid>.json status=idle or Stop hook); cancel only if mid-LLM-stream
 3 flush:   mutagen sync flush; ship last transcript lines; git stash create; secrets diff
 4 verify:  target reports (last_record_uuid, tree_hash, secrets_hash) == source stamp
 5 commit:  coordinator CAS owner=homelab, epoch=e+1   <- the only atomic step
 6 fence:   source hooks now deny; source process told to stop (continue:false + send-key / claude stop)
 7 activate: target relaunches recorded processes (dev server spec) in Rex splits, then
            rex split … exec claude --resume <standby path> --remote-control <repo> "<restore-context note>"
 8 flip:    replica direction reverses; Mac becomes the standby
```

The **expected latency** after quiesce is roughly 1–4 s: well under a second for flush, verify and CAS on a tailnet, plus Claude's start-up. That is an estimate, unbenchmarked. It follows from Clark's result that downtime tracks the residual dirty set, not repo size ([Clark et al.](https://www.usenix.org/event/nsdi05/tech/full_papers/clark/clark_html)). **What it can't do:** it still cannot carry in-memory process state, so dev servers restart and long test runs must finish or re-run. It cannot resume mid-tool-call. It relies on undocumented surfaces: the `sessions/<pid>.json` status schema and the JSONL format. It still produces a new Remote Control entry. And it requires the homelab coordinator to be up before ownership can change. Losing the coordinator freezes moves, but it does not cause split-brain.

### Architecture 3: an agent-agnostic session-bundle spec, adapters and a follow-me relay

The **components** are three pieces. The first is an open **Baton Session Bundle** spec, versioned and modelled on Letta `.af`'s "serialise everything, null the secrets" approach ([agent-file](https://github.com/letta-ai/agent-file)). The second is a set of **adapters**, each exporting and importing an agent's *native* state rather than lossy summaries: `claude-code` (JSONL plus sidecars), `codex` (rollout files, format not yet examined), `opencode` (via `serve` and `attach`), and a generic `acp` adapter that relies on `session/load` replay. The third is a **self-hosted relay** on the homelab. Clients subscribe to it by a stable baton session ID and receive a snapshot followed by a live tail (ACP `session/load` replay, or AG-UI `MessagesSnapshot` plus deltas). When a session moves, the relay rebinds the ID to the new runtime and pushes a resync snapshot. Content is end-to-end encrypted with per-session data keys, as Happy does ([Happy encryption](https://github.com/slopus/happy/blob/main/docs/encryption.md)). Reachability uses T3-style ordered routes, LAN then tailnet then optional tunnel ([T3 remote.md](https://github.com/pingdotgg/t3code/blob/main/docs/internals/remote.md)). The cut-over is Architecture 2's sequence, with step 7 extended by "relay rebinds and clients resync". Clients see a reconnect of a few seconds, not a new thread.

**What it can't do:** cross-*agent* moves (Claude → Codex) remain summaries, as T3's own docs concede ([T3 context-handoffs.md](https://github.com/pingdotgg/t3code/blob/main/docs/internals/context-handoffs.md)). ACP's remote transport is not yet stable. Claude-specific surfaces (Remote Control, Desktop) will not follow the relay's ID. It is also a much larger maintenance surface, in a category where hosted projects die. The relay should therefore stay optional and self-hosted, with Remote Control remaining the zero-effort phone path for Claude.

## Conclusion

The research reframes the problem. "Live migration" of a coding agent is not a process problem at all. It is a **consistency and ownership problem over three small datasets**: an append-only journal, a working tree, and a secrets manifest. Once it is framed that way, forty-year-old ideas solve it: pre-copy with a short stop-and-copy (Clark), fencing tokens (Kleppmann), and replay-from-ack streams (Eternal Terminal). Claude Code's hooks happen to provide exactly the fencing points the theory requires. The second insight is economic. Because the prompt cache keys on exact bytes rather than on the host, the cheapest and most faithful handoff is the one that **never edits history and only appends**. Path rewriting, the default move of every existing migrator, quietly costs a full context re-write and couples you to a format Anthropic calls internal. Mirroring the Mac's directory layout to the homelab's turns that into a one-time filesystem decision rather than a per-handoff cost.

For your setup the division of labour is now clear. Rex launches, hosts and shows the resumed session. Remote Control keeps the phone attached. Tailscale (SSH or an encrypted drop) moves bytes. age keys decide who can read secrets. Every existing tool has stopped short at the same two pieces, single-owner fencing and an explicit secrets manifest, so those two are where an open-source tool earns its place. Building Architecture 1 this week, after running the Phase 0.5 spikes, gets you seconds-scale handoffs now and makes the later tiers incremental rather than speculative.
