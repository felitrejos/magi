# Claude Code session state and first-party cross-host session mechanisms (as of Nov 2026)

Scope note: "Docs" = code.claude.com official docs fetched 2026-11-14. "Changelog" = the official Claude Code CHANGELOG (cached locally at `~/.claude/cache/changelog.md`, mirrors https://github.com/anthropics/claude-code/blob/main/CHANGELOG.md; latest entry 2.1.319). "Observed locally" = read-only inspection of this Mac (Claude Code CLI 2.1.319 installed; running Desktop-hosted sessions report 2.1.325). Credential files were not opened.

## Q1. Where transcripts live, how the project dir is derived, and what breaks when the absolute path differs

### Takeaway
Transcripts are `~/.claude/projects/<encoded-cwd>/<session-uuid>.jsonl`, where `<encoded-cwd>` is the absolute cwd with every non-alphanumeric char replaced by `-` (truncated to 200 chars + hash if longer). Since v2.1.223, `claude --resume <id>` searches every project dir on the machine, and `claude --resume <absolute-path-to.jsonl>` resumes a file directly, so the dir name no longer has to match; but the JSONL still embeds the absolute `cwd` on nearly every record, `~/.claude.json` keys per-project state by absolute path, and file-history records absolute parent dirs, so a Mac→Linux move with a different path needs path rewriting (or an identical path on both hosts) for a faithful resume.

### Cited Findings
- Storage location: "Claude Code stores transcripts as JSONL at `~/.claude/projects/<project>/<session-id>.jsonl`, where `<project>` is your working directory path with non-alphanumeric characters replaced by `-`. For a working directory whose converted name exceeds 200 characters, Claude Code truncates the name to 200 characters and appends a hash of the full path." — [Docs: Manage sessions](https://code.claude.com/docs/en/sessions)
- Example from SDK docs: `/Users/me/proj` becomes `-Users-me-proj`; storage moves under `$CLAUDE_CONFIG_DIR/projects/` if `CLAUDE_CONFIG_DIR` is set. — [Docs: Agent SDK sessions](https://code.claude.com/docs/en/agent-sdk/sessions)
- `CLAUDE_CODE_PROJECT_DIR_NAME` (v2.1.234+) lets you pin the project dir name, but only works together with `CLAUDE_CONFIG_DIR`, must be 1-64 `[A-Za-z0-9_-]`, and is read once from the launching shell env (not from a settings `env` block). With it set, transcripts and auto memory go to `$CLAUDE_CONFIG_DIR/projects/<name>/` "whatever the working directory is". — [Docs: Manage sessions](https://code.claude.com/docs/en/sessions)
- Resume lookup order for `claude --resume <session-id>`: (1) current project dir and its git worktrees, (2) every other project on this machine. "The cross-project search resolves the ID only when exactly one other project holds a transcript with messages for it, so a hand-copied duplicate makes Claude Code report not-found rather than resume an arbitrary copy." — [Docs: Manage sessions](https://code.claude.com/docs/en/sessions)
- `claude --resume <transcript-path>` "Resumes the session stored in the `.jsonl` transcript file at that absolute path." — [Docs: Manage sessions](https://code.claude.com/docs/en/sessions)
- Cross-dir lookup arrived in v2.1.223; "Before v2.1.223, the lookup was scoped to the current project directory and its git worktrees" (older behavior). — [Docs: Agent SDK sessions](https://code.claude.com/docs/en/agent-sdk/sessions)
- Officially sanctioned cross-host recipe: "Persist `~/.claude/projects/<encoded-cwd>/<session-id>.jsonl` from the first run and restore it inside any directory under `~/.claude/projects/` on the new host before calling `resume`." Also: "Session files are local to the machine that created them." — [Docs: Agent SDK sessions, "Resume across hosts"](https://code.claude.com/docs/en/agent-sdk/sessions)
- SDK `SessionStore` adapter mirrors transcripts to your own backend; "The store lookup key derives from the working directory, so resume from a `cwd` matching the original run's." — [Docs: Agent SDK sessions](https://code.claude.com/docs/en/agent-sdk/sessions)
- When resuming a session from an unrelated project via the picker, "Claude Code copies a `cd` and resume command to your clipboard instead. If that project's directory no longer exists, Claude Code resumes the session in your current directory." `/cd` "relocates it to the new directory's project storage." — [Docs: Manage sessions](https://code.claude.com/docs/en/sessions)
- The JSONL format "is internal to Claude Code and changes between versions, so scripts that parse these files directly can break on any release." — [Docs: Manage sessions](https://code.claude.com/docs/en/sessions)
- Community: project dirs are keyed by absolute path and the JSONL lines carry the old absolute `cwd`; renaming the folder doesn't update it; `~/.claude.json` `projects` map is keyed by absolute path and must be re-keyed; paths also appear inside message bodies; macOS is case-insensitive while Linux is not; logins must be redone on the new host. — [DEV Community article (Aug 2026)](https://dev.to/gowtham-sai-yadav/why-you-cannot-copy-a-claude-code-session-to-another-machine-2008)
- Community tool `claude-code-migrate` copies `projects/` (incl. subagents), `settings.json`, `todos/ tasks/ shell-snapshots/ file-history/ paste-cache/ image-cache/ session-env/` and a `~/.claude.json` snapshot; for different usernames it renames slug dirs and `sed`-rewrites `/Users/<old>/`→`/Users/<new>/` in transcripts and `~/.claude.json`; its remap rewrites "cwd, file_path, command strings". States same-absolute-path restores "just work"; tested only on macOS, Linux untested. — [GitHub: emreonal11/claude-code-migrate](https://github.com/emreonal11/claude-code-migrate)
- Open GitHub feature requests for native cross-machine portability/export (e.g. #18645 export/import, #45447 relative path resolution, #51337 native cross-machine continue) and bug reports that moving a project dir yields "No conversations found to resume" (#27473). — [anthropics/claude-code#18645](https://github.com/anthropics/claude-code/issues/18645), [anthropics/claude-code#27473](https://github.com/anthropics/claude-code/issues/27473), [claudeissues mirror #45447](https://claudeissues.com/issue/45447-feature-cross-machine-session-portability-relative-path-resolution-for-project-c), [claudeissues mirror #51337](https://claudeissues.com/issue/51337-native-support-for-continuing-a-session-across-machines) (status of these not verified; #27473 predates the v2.1.223 cross-dir lookup)

#### Observed locally (this Mac, read-only; record types/keys only)
- `~/.claude/projects/` has 68 entries, 1.8 GB. Dir names are exactly the encoding above, e.g. `-Users-felipetrejos-Developer-Personal-autOScan-lab-autOScan-engine`; a cwd under `~/Library/Application Support/...` encodes spaces as `-` too.
- Per-session layout: `<proj>/<uuid>.jsonl` plus a sibling dir `<proj>/<uuid>/` containing `subagents/agent-<id>.jsonl` + `agent-<id>.meta.json` (meta keys: agentType, description, finished, isBuiltIn, pickedEffortModel, requestNonInteractive, requestShape, spawnDepth, toolUseId), `tool-results/<id>.txt` (spilled large tool outputs), `custom-title.json`, and in some projects `workflows/`. `<proj>/memory/` holds auto memory.
- One 23 MB, 3,097-line transcript (CLI 2.1.317/2.1.325, Desktop entrypoint) had record types: `user` 510, `assistant` 917, `attachment` 249, `system` 87 (subtypes `stop_hook_summary`, `compact_boundary`, `api_error`), `file-history-snapshot` 85, `file-history-delta` 3, `api-request` 194, `api-request-blob` 243, `api-request-shape` 1, `queue-operation` 120, and per-session metadata records repeated ~97× each: `custom-title`, `agent-name`, `mode`, `last-prompt`, `pr-link`, `bridge-session`, `atis-latch`; plus `cost-state`, `tools-used`.
- Message-record keys (user/assistant/attachment/system): `uuid`, `parentUuid` (records form a linked list/tree; compaction adds `logicalParentUuid`), `sessionId`, `timestamp`, `type`, `cwd` (absolute), `gitBranch`, `version` (CLI version), `entrypoint` (e.g. `claude-desktop`), `userType`, `isSidechain`. Assistant adds `message`, `requestId`, `requestRef`, `requestedModel`, `effort`, `promptCacheRequested`, `thinkingDurationMs`, `wireToolInputs`, etc. User tool results add `toolUseResult` (e.g. Bash: stdout/stderr/interrupted; Edit: filePath/oldString/newString/originalFile/structuredPatch), `sourceToolAssistantUUID`, `permissionDecision`, `promptId`.
- Content block types: `text`, `thinking`, `tool_use`, `tool_result`, `image`, plus `tool_addition`/`tool_removal` (deferred-tool deltas).
- `api-request` records store `params` (betas, context_management, max_tokens, model, output_config, thinking), `cacheControl` breakpoints (e.g. `ttl:"1h"`, one with `scope:"global"`), `keep`, `base`, `tail`, `requestDigest`, `shapeHash`, `querySource`; `api-request-blob` stores hashed message blobs. Attachments include `prompt_snapshot` (keys: systemPrompt, tools, systemTurns, inlineTools, keptReminders, …), `environment` (snapshot: workingDirectory, additionalWorkingDirectories, isGitRepo, isWorktree, platform, osVersion, shell, scratchpadDirectory), `session_context`, `deferred_tools_record`, `mcp_instructions_delta`, `skill_listing`, `task_status`, `remote_session_change`, `credential_org`.
- `bridge-session` record keys: `bridgeSessionId` (a `cse_…` id), `lastSequenceNum`, `ownerAccountUuid`, `ownerOrganizationUuid` — i.e. the transcript records the Remote Control/cloud bridge binding and account owner.
- `compact_boundary` `compactMetadata` keys: trigger, preTokens, postTokens, preservedMessages, preservedSegment, cumulativeDroppedTokens, preCompactDiscoveredTools, preCompactArtifactReadVersions, durationMs.
- `file-history-snapshot` → `snapshot.trackedFileBackups` map: key is a (relative-looking) file path, value `{backupFileName:"<16hex>@v<N>", version, backupTime, realParentDir}` where `realParentDir` is an absolute path; backup blobs live in `~/.claude/file-history/<session-uuid>/<hash>@v<N>`. `file-history-delta` keys: backup, messageId, snapshotMessageId, trackingPath.
- In one session, the absolute cwd string appeared on 46 lines and absolute home paths appeared in tool_use inputs; distinct `cwd` per session was 1 (it changes only if `/cd` is used).

### Inferences
- For a Mac (`/Users/x/Developer/Personal/stampr`) → Linux (`/home/x/developer/stampr/stampr`) move, simply dropping the JSONL into any `~/.claude/projects/*/` dir on Linux and running `claude --resume <uuid>` (or `--resume /abs/path.jsonl`) from the new checkout should load the conversation on v2.1.223+, but: the model will see stale absolute paths in history (old tool_use inputs, `environment` attachment, prompt_snapshot), `--resume` from the picker would try to `cd` to a nonexistent dir (docs: falls back to current dir), `/rewind` code-restore would point at nonexistent `realParentDir`s, and the `~/.claude.json` project entry (trust, allowedTools, MCP enablement) would not match. A transfer tool should either (a) keep an identical absolute path on both hosts (e.g. symlink `/Users/x/...` on Linux), or (b) rewrite `cwd`/path strings (JSON-escaped) in the JSONL, rename the project dir, and re-key `~/.claude.json`.
- Because records also embed `version`, `entrypoint`, `bridgeSessionId`, and owner account/org UUIDs, the destination must run a same-or-newer CLI and be signed into the same account for Remote Control rebinding.
- Using `CLAUDE_CONFIG_DIR` + `CLAUDE_CODE_PROJECT_DIR_NAME` on both hosts would make the project dir name path-independent (but does not fix `cwd` embedded in records).

### Gaps
- No official doc enumerates which JSONL fields must be rewritten for a different cwd; the format is declared internal/unstable.
- Not verified empirically whether resuming a transcript whose `cwd` differs from the current dir causes Claude Code to warn, rewrite, or `cd` (only picker behavior is documented).

## Q2. Other per-session / per-project state and what's needed to resume faithfully

### Takeaway
Only the transcript JSONL (plus its `<uuid>/subagents` and `<uuid>/tool-results` sidecars) is required to resume the conversation; `file-history/<uuid>/` is needed for `/rewind` code restore; `tasks/`, `plans/`, project `memory/`, `~/.claude.json` project entry, settings and CLAUDE.md files restore environment fidelity. Shell snapshots, session-env, `sessions/<pid>.json`, sockets and keys are host/process-local and should be regenerated, not copied.

### Cited Findings
- Retention-swept app data (default `cleanupPeriodDays` 30, min 1): `projects/<project>/<session>.jsonl` (transcript incl. "the system prompt, tool definitions, and parameters of the requests"), `.orphaned-…`/`.superseded-…` copies, `projects/<project>/<session>/subagents/`, `…/tool-results/`, `…/mcp-tasks/` ("What a resumed session needs to follow its running MCP tasks again"), `file-history/<session>/` ("Pre-edit snapshots… used for checkpoint restore… 100 most recent checkpoints"), `plans/`, `debug/`, `paste-cache/`, `image-cache/<session>/` (≤2.1.274; later images go under the temp dir), `uploads/<session>/` (Remote Control attachments), `dev-mods/<session>/`, `session-env/` ("Per-session environment metadata"), `tasks/` ("Task lists written by the task tools"), `shell-snapshots/` ("Aliases, functions, and shell options captured at startup… Removed on clean exit"), `backups/` (`~/.claude.json` copies). `todos/`, `statsig/`, `logs/` are "Legacy directories from older versions. No longer written." — [Docs: .claude directory](https://code.claude.com/docs/en/claude-directory)
- `sessions/` "holds one small file per running session, used to detect concurrent sessions and crashes"; removed at exit. `jobs/` and `daemon/` hold background-session state; `.credentials.json` holds login credentials (Linux/Windows; macOS uses keychain). Kept until deleted: `history.jsonl` (prompts with project path), `stats-cache.json`, `remote-settings.json`, `policy-limits.json`. — [Docs: .claude directory](https://code.claude.com/docs/en/claude-directory)
- Auto memory is `projects/<project>/memory/` and is not age-swept. Scratchpad lives in temp: macOS `/private/tmp/claude-<uid>/<project>/<session-id>/scratchpad/`, Linux `/tmp/claude-<uid>/<project>/<session-id>/scratchpad/`. — [Docs: .claude directory](https://code.claude.com/docs/en/claude-directory)
- `~/.claude.json`: "App state, account details, UI toggles, personal MCP servers"; `claude purge` deletes the project's transcripts+memory, per-session `tasks/`, `debug/`, `file-history/`, matching `history.jsonl` lines, and "The project's entry in `~/.claude.json`" (trust, history, MCP servers); it leaves `shell-snapshots/` and `backups/` because they are not project-scoped. — [Docs: .claude directory](https://code.claude.com/docs/en/claude-directory)
- What resume restores: conversation history (from last compaction summary onward), model, `--agent`, permission mode (with exceptions: `bypassPermissions` is not restored; `auto` only if still eligible), active goal, unexpired session-scoped scheduled tasks. "Background Bash and monitor tasks aren't." Background subagents/Bash/workflows that died with the previous process appear as "a note that it didn't finish". Interrupted tool calls are not rerun. — [Docs: Manage sessions](https://code.claude.com/docs/en/sessions)
- Not restored from launch flags: `--mcp-config`, `--settings`, `--plugin-dir`, `--fallback-model`, `--add-dir`, and mid-session `/add-dir`; "settings.json and settings.local.json are re-read at launch". — [Docs: Manage sessions](https://code.claude.com/docs/en/sessions)
- `--fork-session` / `/branch`: new session ID; "Allow for this session" grants carry over in `/branch` (same process) but a separate `--fork-session` process "starts without them". "If you resume the same session in two terminals without forking, messages from both interleave into one transcript." — [Docs: Manage sessions](https://code.claude.com/docs/en/sessions)
- System prompt snapshot (`--system-prompt-snapshot on`, the default except under `--bare`): "the prompt is rendered on the conversation's first request… and recorded; every later request and resume sends the record as-is, even when a later launch passes different text, until the conversation is compacted." — Observed locally in `claude --help` (v2.1.319); consistent with [Docs: prompt caching, Resuming a session](https://code.claude.com/docs/en/prompt-caching)
- Project-scoped agents on resume are looked up in "the session's original directory… and then the directory you resume from." — [Docs: Manage sessions](https://code.claude.com/docs/en/sessions)

#### Observed locally
- `~/.claude/` top level: `.claude.json` (944 B, inner), `CLAUDE.md`, `settings.json`, `history.jsonl` (191 KB), `stats-cache.json`, `mcp-needs-auth-cache.json`, `daemon.log`, `.last-cleanup`, `.last-update-result.json`; dirs `backups/` (5 rotating `.claude.json.backup.<ts>`), `cache/` (changelog.md, model-catalog/), `daemon/` (`control.key`, `roster.json` keys proto/supervisorPid/updatedAt/workers, `attach-journal/`, `dispatch/`), `debug/`, `file-history/` (8.2 MB; dirs named by session UUID), `ide/`, `jobs/` (`pins.json`), `paste-cache/`, `plugins/` (20 MB), `projects/` (1.8 GB), `session-env/` (94 empty UUID-named dirs), `sessions/`, `shell-snapshots/` (`snapshot-zsh-<ms>-<rand>.sh`, ~7 KB each), `skills/` (4.6 MB), `spares/`, `state/`, `telemetry/`, `uploads/` (11 MB). No `.credentials.json` on this Mac (keychain). `~/.claude.json` (213 KB) + `.backup` also in `$HOME`.
- `sessions/<pid>.json` keys: pid, sessionId, cwd, startedAt, procStart, version, peerProtocol, peerFeatures, kind, entrypoint, hostSessionId, pidDomain (`darwin`), messagingSocketPath (`/tmp/cc-socks/<pid>.sock`), name, status, updatedAt, bridgeSessionId (`session_…`). Alongside are `<pid>.<sha256>.key` files (not read). These are pure process/host-local liveness records.
- `~/.claude.json` per-project entry keys (keyed by absolute path; 51 projects): allowedTools, hasTrustDialogAccepted, enabledMcpjsonServers, disabledMcpjsonServers, mcpServers, mcpContextUris, lastSessionId, lastCost/lastDuration/last*Tokens, exampleFiles, hasClaudeMdExternalIncludesApproved. Top level also holds `oauthAccount`, `userID`, `machineID`, `anonymousId`, global `mcpServers`, `githubRepoPaths`, feature-flag caches, `hasUsedRemoteControl`, `remoteControl*` keys.
- Shell snapshot is a generated zsh script ("# Snapshot file", `unalias -a`, then aliases/functions/options) — host-shell-specific; a Linux bash host would generate its own.

### Inferences
- Minimal faithful transfer set per session: `projects/<enc>/<uuid>.jsonl`, `projects/<enc>/<uuid>/` (subagents, tool-results, mcp-tasks), `projects/<enc>/memory/`, `file-history/<uuid>/` (only if rewind matters), relevant `tasks/<list>/`, `plans/` files referenced, `uploads/<uuid>/` if RC attachments are referenced by path. Plus project config that already travels with git (`CLAUDE.md`, `.claude/settings.json`, `.mcp.json`) and non-git `.claude/settings.local.json`, and the `~/.claude.json` project entry (re-keyed to the new path) for trust/MCP enablement. User-level `~/.claude/settings.json`, `CLAUDE.md`, skills, plugins, agents should be synced separately (they're host-level, not session-level).
- Do not copy: `sessions/`, `session-env/`, `shell-snapshots/`, `daemon/`, `*.key`, `backups/`, credentials, `machineID`.

### Gaps
- Contents/semantics of `session-env/` dirs are undocumented beyond "per-session environment metadata" (all observed empty).
- Whether `tasks/` lists are keyed by session ID or a shared list ID was not verified.

## Q3. How --resume / --continue / --fork-session / --session-id / SDK resume work; can a copied JSONL be resumed elsewhere; gotchas

### Takeaway
Resume replays the transcript (from last compaction) as the new request prefix; a JSONL copied to another host is officially resumable ("restore it inside any directory under `~/.claude/projects/` on the new host"), but filesystem state, background processes, launch-flag config, and non-restored permission grants do not come along, and stale absolute paths remain in history.

### Cited Findings
- CLI flags (observed `claude --help`, v2.1.319): `-c/--continue` "Continue the most recent conversation in the current directory"; `-r/--resume [value]` "by session ID or name, or open interactive picker"; `--fork-session` "When resuming, create a new session ID instead of reusing the original"; `--session-id <uuid>` "Use a specific session ID"; `--no-session-persistence` (print only); `--bg` "With --resume <session-id>, continues that session in the background under the same ID, or starts a copy… when the session is already running"; `--teleport [session]`; `--cloud [description|session_id|url]`; `--remote-control [name]`; `--desktop` (open in Desktop app with `--continue`/`--resume <id>`); `--environment <ccpool_…>` (new cloud session on a self-hosted environment); `--exclude-dynamic-system-prompt-sections`; `--system-prompt-snapshot <on|off>`. Subcommands: `remote-control`, `attach`, `logs`, `stop`, `respawn`, `rm`, `agents`, `purge`, `self-hosted-runner`.
- `claude --continue` / picker skip `-p` and Agent SDK sessions (resume them by explicit ID); `claude -p --continue` includes them. — [Docs: Manage sessions](https://code.claude.com/docs/en/sessions)
- SDK: `continue` = most recent session in cwd; `resume` = specific ID; `forkSession`/`fork_session` = new session with copy of history; `persistSession: false` (TS) for no disk writes. "Sessions persist the conversation, not the filesystem." "Forking branches the conversation history, not the filesystem." — [Docs: Agent SDK sessions](https://code.claude.com/docs/en/agent-sdk/sessions)
- SDK provides `listSessions()/getSessionMessages()/getSessionInfo()/renameSession()/tagSession()` (TS) and Python equivalents, and a `SessionStore` adapter for mirroring transcripts to shared storage for cross-host resume. — [Docs: Agent SDK sessions](https://code.claude.com/docs/en/agent-sdk/sessions)
- Compaction gotcha: after compaction, resume loads only the last summary + preserved messages + later messages; "The messages that the last compaction summarized aren't loaded again." — [Docs: Manage sessions](https://code.claude.com/docs/en/sessions)
- Changelog gotchas: "Fixed `--resume`… moving a session on a model name Claude Code doesn't recognize to a different model" (model ID compatibility across versions); "Fixed sessions moved to the background while idle reopening as 'no saved transcript' after a restart"; "Fixed resuming a conversation from before `/clear` reattaching to the Remote Control session of the conversation after it"; "Fixed `/rewind` failing with 'No files were restored' when restoring code to a checkpoint from before `/branch`"; "Fixed a case where `/rewind` could restore or delete a file through a directory symlink"; `sed -i` and other Bash edits are "no longer restored by `/rewind`" (only Claude's file-tool edits are checkpointed). — [Changelog](https://github.com/anthropics/claude-code/blob/main/CHANGELOG.md)
- Remote Control and resume: if you resume in a second terminal while the first still has RC on, the second prints "Remote Control not started here"; run `/remote-control` there to move RC to it. — [Docs: Remote Control](https://code.claude.com/docs/en/remote-control)
- Community: copying JSONL between macOS and NixOS reportedly did not produce a working resume (pre-v2.1.223-era reports); username change breaks resume because encoded paths differ. — [WebSearch summary of anthropics/claude-code issues incl. #18645](https://github.com/anthropics/claude-code/issues/18645)

### Inferences
- tool_use IDs (`toolu_…`) and message `uuid`/`parentUuid` chains are host-independent and safe to copy verbatim; the hazard is only filesystem paths and host facts (cwd, platform, shell, OS version in the `environment` attachment). Because the system prompt is snapshotted per conversation, a resumed session on Linux will keep the Mac-era system prompt (with darwin env facts if those were in it) until compaction; per docs the cwd/platform/shell "announcement" is in the conversation, so the model may keep believing it is on macOS unless a new note is injected (e.g. via a first resume prompt or SessionStart hook output).
- A move tool should end the source process (or ensure it is idle) before copying, since concurrent writers interleave into the same JSONL; or use `--fork-session` on the destination to keep IDs distinct.

### Gaps
- No documentation of how Claude Code reacts when the recorded `cwd` differs from the actual cwd on `--resume <id>` (warn vs silent). Should be tested empirically.
- Whether `--session-id <uuid>` can be used to "adopt" a copied transcript ID (vs. creating a new one) is undocumented.

## Q4. First-party cross-host features (Nov 2026) and their limits for a Mac → self-hosted Linux server move

### Takeaway
None of the first-party features moves a live local CLI session (with full history and process state) to a user-owned server. Remote Control relays a session that keeps running where it started; `--teleport` pulls cloud→local only (and requires a GitHub-pushed branch); `--cloud`/Desktop "Open in > Cloud" start a new cloud session (Desktop carries history only as a summary); self-hosted runners execute cloud sessions on your infra and can move sessions between runners, but are Team/Enterprise public beta and route only cloud-started sessions.

### Cited Findings
**Remote Control (`claude remote-control`, `claude --remote-control`, `/remote-control` / `/rc`)**
- "Claude keeps running locally the entire time"; clients are claude.ai/code and the Claude iOS/Android app (and Desktop app). — [Docs: Remote Control](https://code.claude.com/docs/en/remote-control)
- Architecture: "Your local Claude Code session makes outbound HTTPS requests only and never opens inbound ports on your machine. When you start Remote Control, it registers with the Anthropic API and polls for work… the server routes messages between the web or mobile client and your local session over a streaming connection." "All traffic travels through the Anthropic API over TLS." While connected "the session transcript… is stored on Anthropic servers." — [Docs: Remote Control](https://code.claude.com/docs/en/remote-control)
- Limits: requires claude.ai subscription login (not API key, not Bedrock/Vertex/Foundry, not a custom `ANTHROPIC_BASE_URL`); off by default on Team/Enterprise until an Owner enables it; one remote session per interactive process (server mode supports many, default capacity 32); "Local process must keep running… If you run `claude` from a terminal on a remote machine, start it inside `tmux` or `screen`"; server mode gives up after ~10 min network outage; `claude remote-control --continue`/`--session-id` bring sessions back for "about four hours after the server stopped". — [Docs: Remote Control](https://code.claude.com/docs/en/remote-control); `claude remote-control --help` (observed locally)
- `claude remote-control` spawn modes `same-dir|worktree|session`; session names default to hostname prefix. — observed `claude remote-control --help`
- Implication documented by Anthropic: "To run Claude Code on your own always-on machine and drive it from other devices, use Remote Control." — [Docs: Self-hosted environments](https://code.claude.com/docs/en/self-hosted-environments)

**Cloud sessions / Claude Code on the web, `--cloud`, `--teleport`**
- "From the CLI, session handoff is one-way: you can pull cloud sessions into your terminal with `--teleport`, but you can't push an existing terminal session to the cloud." `--cloud "<task>"` creates a *new* cloud session that clones the GitHub remote at the current branch ("not your local checkout"); with no remote / no GitHub App it uploads a git bundle (<100 MB, untracked files excluded, credential-like files' uncommitted changes left behind). `--remote` is a deprecated alias. — [Docs: Use Claude Code in the cloud](https://code.claude.com/docs/en/claude-code-on-the-web)
- Teleport requirements: clean git state (offers stash), same repository (not fork), branch pushed to remote, same claude.ai account; fetch never prompts for SSH passphrase. Compacted cloud sessions bring only the summary. "The terminal gets its own copy of the session: new work there stays local." "`--teleport` connects through the same Remote Control session infrastructure that cloud sessions use." — [Docs: Use Claude Code in the cloud](https://code.claude.com/docs/en/claude-code-on-the-web)
- `claude -p "msg" --cloud <session-id>` queues a message into an existing cloud session from any machine; "sends no local session state". — [Docs: Use Claude Code in the cloud](https://code.claude.com/docs/en/claude-code-on-the-web)
- Cloud env expiry: reopening restores conversation history; not restored: running shell commands, subagents, session-scoped scheduled tasks/`/loop`. — [Docs: Use Claude Code in the cloud](https://code.claude.com/docs/en/claude-code-on-the-web)
- Not available with ZDR/HIPAA/CMEK orgs or third-party providers. — [Docs: Use Claude Code in the cloud](https://code.claude.com/docs/en/claude-code-on-the-web)

**Desktop app**
- "Open in > Cloud" continues a local Desktop session "as a cloud session, with your conversation carried over as a summary"; dialog states whether files move and whether the local session is archived. "You can't move a session that runs over SSH or in WSL this way." — [Docs: Desktop](https://code.claude.com/docs/en/desktop)
- Desktop SSH sessions run Claude Code on a remote Linux/macOS host (auto-installed), with Desktop as UI; no documented move between local and SSH environments. — [Docs: Desktop](https://code.claude.com/docs/en/desktop)
- `claude --desktop` opens the Desktop app on cwd or on a session with `--continue`/`--resume <id>` (same machine). — `claude --help` (observed) and [Changelog](https://github.com/anthropics/claude-code/blob/main/CHANGELOG.md)

**Self-hosted environments / runners (`claude self-hosted-runner`, `--environment ccpool_…`)**
- Public beta, Team and Enterprise only, off by default. A runner polls `api.anthropic.com` (outbound only), claims a session, clones the repo, spawns a child Claude Code process; "If the runner stops polling, its lease lapses after about 60 seconds… requeue the session for another runner." Runners can release idle/retiring sessions "so the session resumes on a fresh runner when the user sends their next message"; "Anthropic stores the session transcript so you can resume the session from another supported surface." Repo checkouts/files stay on your infra. — [Docs: Self-hosted environments](https://code.claude.com/docs/en/self-hosted-environments)
- Runner CLI (observed `claude self-hosted-runner --help`): `--environment-secret-file`, `--capacity` (default 1), `--base-dir` (default `/workspace`), `--exec-path`, `--hooks-dir` (checkout/command/post-session hooks), `--lock-to-account`, `--client-label`, `--agent-proxy-url`.
- Changelog confirms cross-machine session moves within this system: "Self-hosted runner: Fixed an MCP server that was switched off coming back on after the session moved to a new machine"; "Added `CLAUDE_RUNNER_SPAWN_REASON`… (e.g. `runner_lost`, `resumed`)"; "Added `--hold-idle-file` and `--max-hold-min`… to keep an idle session while your host reports processes it left running." — [Changelog](https://github.com/anthropics/claude-code/blob/main/CHANGELOG.md)

**Background sessions / agent view (same machine)**
- `claude --bg`, `claude agents`, `attach`, `logs`, `stop`, `respawn`, `rm`; state in `~/.claude/jobs/` and `~/.claude/daemon/`. Local only. — `claude --help` (observed); [Docs: .claude directory](https://code.claude.com/docs/en/claude-directory)

**/export**
- "`/export` … copy the current conversation to your clipboard or save it as a plain-text file, with messages and tool outputs rendered as readable text" — human-readable, not resumable. — [Docs: Manage sessions](https://code.claude.com/docs/en/sessions)

### Inferences
- For a Pro/Max individual moving a live Mac session to a home Linux server, the only first-party building blocks are: (1) copy transcript + `claude --resume` on the server (documented for SDK, works for CLI by ID or absolute path), then (2) `/remote-control` or `claude --remote-control` on the server to keep driving it from phone/browser/Desktop. Self-hosted runners would be the closest "native" mover but are Team/Enterprise-only, accept only cloud-originated sessions, and require a GitHub/pushed repo.
- Remote Control's bridge binding is recorded in the transcript (`bridge-session` record). After moving, the source must release RC (stop the process) before the destination can take it; docs say a second resume prints "Remote Control not started here" while the first still holds it.

### Gaps
- No first-party "push local session to my own server" or "local → self-hosted runner" handoff was found in docs or changelog.
- Unclear whether RC on the destination reuses the same `bridgeSessionId` (same claude.ai/code thread) after a cross-host resume or creates a new remote session; not tested.

## Q5. Prompt cache behavior on resume on a different host

### Takeaway
The API cache is keyed on exact request prefix + model (+ speed/effort on some models) within an organization (and workspace on some providers), not on host; but Claude Code's request content embeds per-machine facts (cwd, platform, shell, OS, auto-memory paths, git status), so "In Claude Code, the cache is effectively scoped to one machine and directory." A resume replays the stored prompt snapshot and history, so if the prefix bytes are identical and within TTL (5 min, or 1 h on subscriptions for the main conversation) it will hit cache regardless of host.

### Cited Findings
- "The API caches by matching the start of each request… The match is exact, so a change anywhere in the prefix recomputes everything after it." — [Docs: Prompt caching](https://code.claude.com/docs/en/prompt-caching)
- "Caches are isolated between organizations, and on some providers, between workspaces within an organization. Within those boundaries, two requests share a cache only when their model, speed, and prefix match." — [Docs: Prompt caching, Cache scope](https://code.claude.com/docs/en/prompt-caching)
- "In Claude Code, the cache is effectively scoped to one machine and directory. The system prompt embeds your auto memory paths, and the conversation opens with an announcement of the working directory, platform, shell, and OS version." — [Docs: Prompt caching, Cache scope](https://code.claude.com/docs/en/prompt-caching)
- Resume: "Claude Code sends the whole conversation again, and the request reads from the cache whatever part of its prefix is unchanged and still within the cache lifetime… By default, the resumed conversation keeps the system prompt it started with." — [Docs: Prompt caching, Resuming a session](https://code.claude.com/docs/en/prompt-caching)
- TTL: subscription within plan usage → main conversation 1 h, else 5 min; override with `promptCacheTtl` / `CLAUDE_CODE_PROMPT_CACHE_TTL` (`5m`/`1h`, v2.1.242+). Model switch, some effort changes, fast-mode toggle, tool-definition changes (MCP connect when tools aren't deferred), plugin MCP changes, compaction and upgrades invalidate. With deferred tool search, "Claude Code keeps the tool list from the conversation's first request for the whole conversation." — [Docs: Prompt caching](https://code.claude.com/docs/en/prompt-caching)
- `--exclude-dynamic-system-prompt-sections`: "Move per-machine sections (cwd, env info, memory paths, git status) from the system prompt into the first user message. Improves cross-user prompt-cache reuse." — `claude --help` (observed, v2.1.319); see also [Docs: Agent SDK modifying system prompts](https://code.claude.com/docs/en/agent-sdk/modifying-system-prompts)
- Local observation: `api-request` records carry `cacheControl` breakpoints with `ttl:"1h"` and one with `scope:"global"` on a system block.

### Inferences
- A copied transcript resumed on Linux within the TTL, by the same account/org, same model/effort/speed, same CLI version (system prompt snapshot replayed) and same tool set, should hit the existing cache because nothing in the prefix references the host per se; new per-host content (a fresh `environment` attachment, different MCP tool set, different CLI version) appended or inserted would cause partial/full misses. If the tool rewrites embedded paths in historical messages, that changes the prefix from the first rewritten byte and forces a full re-read (cost ≈ one uncached turn of the full context) — an argument for preserving the original path (symlink) instead of rewriting.
- The "Resume this conversation?" dialog (Pro/Max/Ultra) estimates usage cost when the cache is cold. — [Docs: Manage sessions](https://code.claude.com/docs/en/sessions)

### Gaps
- No doc states whether the cache is keyed on the API key / OAuth token vs. org; docs say org (and workspace on some providers). Not tested empirically across hosts.

## Q6. In-flight state that cannot be serialized

### Takeaway
Running background Bash/monitor processes, MCP server processes and their connections, the streaming model response, pending permission prompts/dialogs, shell snapshot/env, and the process-local Remote Control registration are not persisted; resume records unfinished background work as "didn't finish" notes and does not rerun interrupted tools.

### Cited Findings
- "Interrupted tool calls: a tool that was still running when the previous process ended… doesn't get rerun when you resume." "Session-scoped scheduled tasks… are restored. Background Bash and monitor tasks aren't." Background subagents/Bash/workflows that ended with the previous process show up "as a note that it didn't finish". — [Docs: Manage sessions](https://code.claude.com/docs/en/sessions)
- `mcp-tasks/` stores "What a resumed session needs to follow its running MCP tasks again" (server-side MCP tasks only). — [Docs: .claude directory](https://code.claude.com/docs/en/claude-directory)
- Cloud env expiry: not restored — running shell commands, subagents (some resumable), session-scoped scheduled tasks and `/loop`. — [Docs: Use Claude Code in the cloud](https://code.claude.com/docs/en/claude-code-on-the-web)
- "Allow for this session" permission grants don't carry into a separate `--fork-session` process. — [Docs: Manage sessions](https://code.claude.com/docs/en/sessions)
- Self-hosted runners release a mid-turn session only after the turn finishes, wait up to 60 s for background tasks, and "A turn that outlives the kill is still lost." — [Docs: Self-hosted environments](https://code.claude.com/docs/en/self-hosted-environments)
- Shell snapshots are "captured at startup" and "Removed on clean exit". — [Docs: .claude directory](https://code.claude.com/docs/en/claude-directory)
- RC forwarded dialogs (non-permission) expire after five minutes by default; permission prompts and `AskUserQuestion` stay open until answered (only while the process lives). — [Docs: Remote Control](https://code.claude.com/docs/en/remote-control)
- Changelog: "Fixed Remote Control… losing a message still queued when the terminal quit (it now arrives on the next resume)" — queued RC messages are server-side and survive restart. — [Changelog](https://github.com/anthropics/claude-code/blob/main/CHANGELOG.md)

### Inferences
- A "move in seconds" tool should wait for an idle point (no turn streaming, no pending permission prompt, no running background shells/subagents) — mirroring the self-hosted runner's release semantics — then stop the source, transfer files, and resume on the destination; dev servers or long-running Bash jobs must be restarted on the destination by the user or by a resume prompt.
- Queued messages sent via Remote Control are held server-side, so a brief gap during the move need not lose phone-sent prompts, provided the destination re-attaches RC to the same session.

### Gaps
- No documented API to programmatically query "is this session idle / safe to move" other than `sessions/<pid>.json` `status` field (observed locally: `"status":"idle"`, `statusUpdatedAt`) and hooks (Stop/SessionEnd). Stability of that file's schema is undocumented.
